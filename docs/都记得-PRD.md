## 1. 一句话说明产品

**不是家务清单，是家庭责任的所有权交接系统。**

全家人（包括父母、老人、小孩）各自和同一个 AI 聊天，就像现在用豆包一样。AI 在得到本人同意后，把散落在日常对话里的家庭事务沉淀进一个家庭共享数据库，识别出「谁在发现问题、谁在记截止时间、谁在做安排、谁只是执行、谁在跟进」，然后提出把一整块责任交接给明确的主人。交接完成后，提醒直接发给新主人，原来那个人不需要再追问。

同时它承接家里有老人或小孩需要看护的场景：看护人把要点说给 AI，AI 按时提醒被看护人本人，需要回应的事项在超时未回应时自动升级通知其他家庭成员。

## 2. 用户需求与痛点

### 2.1 目标用户

| 角色 | 责任身份 `role` | 典型诉求 |
| --- | --- | --- |
| 家庭主责任人（多为妻子 / 母亲 / 长女） | `primary` | 「事情已经分了，为什么还是我最累」——想真正卸下一块责任，而不是多一个待办 App |
| 共同生活成员（伴侣 / 其他子女） | `partner` | 「你说了我就做」——想明确知道哪一整块归我，不想被反复提醒 |
| 被看护人（老人 / 小孩） | `subject` | 想有个能随时说话的对象；不想被当成被管理的对象；有些事不想让子女知道 |
| 外部照护者（保姆 / 护工，V2） | `caregiver` | 需要交接清楚，需要留痕 |

#### 两个正交的身份维度（V1.1 新增，务必不要混用）

产品里有两个身份字段，它们**不是一回事，也不能互相推导**：

| 字段 | 是什么 | 谁决定 | 用途 |
| --- | --- | --- | --- |
| `familyRole` | **家庭称谓**：妈妈 / 爸爸 / 爷爷 / 奶奶 / 女儿 / 儿子 / 其他 | **用户自己选**，加入时一次，随时可改 | 展示、称呼、头像、Agent 的语气 |
| `role` | **责任身份**：`primary` / `partner` / `subject` | **不问用户，从对话与待办中推断**，见 4.1.5 | 只决定这个人自己的首页形态与提醒策略 |

**这两个字段不能互相推导，这是价值观不是技术洁癖。**如果让 `familyRole = 奶奶` 自动得出 `role = subject`，产品就变成了「按年龄把人归类为被管理对象」，直接违反 4.3.2「被照护者也是有主体性的人」。

硬性规则：

- 用户在界面上**只选家庭称谓**，永远不选、也永远看不到责任身份——既不是 `primary / partner / subject` 这套英文枚举，也不是「主责任人」「被看护人」「共同生活成员」这套中文说法。完整禁用词表见 6.5。

> **文档术语 ≠ 界面文案。**本文档为了把机制说准，会反复使用「主责任人」「被看护人」这类词，第 6.2 节的标题就是「被看护人侧的无障碍要求」。这是规格语言，写给研发和设计看的。**这些词一个都不许出现在产品界面上。**照抄文档术语进 UI 是本项目最容易犯的错，6.5 给了每一个词的替代说法。
- **责任身份不在注册或加入时询问。**问「你是不是家里主要负责的那个人」得不到可靠答案——真正的主责任人往往不觉得自己在承担额外劳动，这恰恰就是隐形劳动的定义。所以它必须从行为里长出来。
- 责任身份是**会变的**。这个月承担最多的人，交接成功之后下个月可能就不是了——这正是产品想看到的变化，所以它必须是持续推断的结果，不能是一次性写死的属性。
- 称谓可以重复。一个空间里出现两个「女儿」是正常的，用称谓 + 名字消歧，不做唯一性约束。

### 2.2 核心痛点

| # | 痛点 | 说明 |
| --- | --- | --- |
| 1 | 家务已经分了，隐形劳动没有分 | 累人的不是洗碗，是永远负责发现下一件事：冰箱快空了、周五要穿白衬衫、妈妈下周该复查了、报告要存好、两周后还要复诊。另一个人确实做了事，但仍在等待安排 |
| 2 | 家庭信息不以任务的形式出现 | 事情藏在「妈最近腿又疼了」「你有空顺便看一下吧」这类句子里。规则引擎解析不了，只能靠一个人时刻在场地接住 |
| 3 | 老人小孩的照护缺一个中间层 | 全靠看护人的记忆和手机闹钟。看护人一旦临时有事整条链就断，而被看护人自己没有被提醒的入口 |
| 4 | 现有工具的数据来源要么不可用，要么越界 | 手动录入等于又是主责任人在干活；读取聊天记录和位置等于变成伴侣监控。两条路都走不通 |

把痛点 1 拆成五个阶段——**发现、记住截止时间、制定安排、执行、跟进结果**——现有的家务 App 全部只在切分第 4 步，没有一个在切分另外四步。这四步就是隐形劳动，也是本产品的全部战场。

### 2.3 产品的解法与来源

设计原则来自一个跨界迁移：**在多 Agent 开发里，只把零碎任务分给不同 Agent，最后仍然需要一个总控不断协调；只有让每个 Agent 对一整块目录承担完整责任，才能真正解耦。**

家庭同理。不要只把「去医院」这个动作分给伴侣，要把「父母复查」这个**责任域**完整交给他。完整所有权包括发现、记住时间、做安排、执行、跟进结果。

这条洞察就是路演的开场：

> 我在管理多个 AI Agent 时发现，只分配零散任务并不能减少管理者的负担。真正有效的是把一整块责任交给一个明确的所有者。后来我意识到，很多家庭也是如此：事情看起来已经分担了，但仍然只有一个人负责记得、安排和提醒。所以我做了《都记得》。

命名与产品主张是同一个词，路演时不需要额外解释：主责任人的首页问「这周，有哪些事一直只有你在记得？」，产品名就是这个问题被解决之后的状态——**都记得**。原名「不是顺手」降级为副标题保留，因为「你有空顺便看一下吧」这句话本身就是痛点的最佳注解。

### 2.4 数据来源的解法：Agent 即入口

不导出聊天记录，不读取后台数据。**全家人直接和这个 AI 聊天**，AI 就是数据入口。

这一条同时解决三件事：

| | 说明 |
| --- | --- |
| 数据是流式的 | 不是一次性快照，责任域可以持续演进 |
| 授权是天然的 | 内容是本人主动说给 AI 的，不存在后台读取 |
| 分发有理由 | 老人本来就在用豆包这类 AI 聊天产品，替换成本极低；对老人侧它本身就是个能说话的对象，有独立价值 |

对不愿意换的成员，主责任人仍可手动转发消息或上传截图补录。**采纳是渐进的，不是全有或全无。**

## 3. 核心用户链路

### 3.1 主链路：从对话到责任交接

```
创建家庭空间 → 邀请成员 → 各成员分别授权

        每个成员与 Agent 的 1:1 对话（+ 可选的家庭群）
                        ↓
        见证：Agent 从自然对话中识别潜在家庭事务，保留原文证据
                        ↓
        同意门：询问本人「要不要让家里人知道这件事」
                （未同意 → 只留在本人侧，不进家庭库）
                        ↓
        聚合：零散信号合并为责任域（如「妈妈的近期健康照护」）
                        ↓
        度量：标注每件事的五个阶段各由谁承担 → 生成本周责任集中度报告
                        ↓
        提议：是否把「X」这个责任域完整交接给某位成员
                        ↓
        交接包：背景 / 历史 / 约束 / 联系人 / 未确定事项 / 下一步 / 证据链
                        ↓
        信息不足或未确认 → blocked（所有权不转移）
                        ↓
        双方确认 → accepted → 此后提醒发给新主人
                        ↓
        原主责任人首页上这条「只有你在记得」消失
```

### 3.2 看护链路（与主链路并行，共用同一个家庭库）

```
看护人对 Agent 说：「奶奶血压药一天两次，饭后吃，别忘了」
                        ↓
        AI 抽取结构化 CareRule 草稿（时间 / 频次 / 是否需回应 / 升级链）
                        ↓
                必须由人确认后才生效  ← 绝不自动激活
                        ↓
        ┌─────────── 确定性状态机接管，以下无任何 LLM ───────────┐
        │  到点 → 提醒被看护人本人（其手机 / Agent 对话页）      │
        │        ↓                                              │
        │  已回应 → 记录闭环                                    │
        │  超时未回应 → 升级 L1（主看护人）                     │
        │        ↓ 仍无响应                                     │
        │  升级 L2（其他家庭成员）→ 建议有人到现场确认           │
        │        ↓                                              │
        │  有人处理 → 闭环记录；始终未处理 → unresolved 留痕     │
        └───────────────────────────────────────────────────────┘
                        ↓
        看护人临时不在：主动声明「我现在有急事」→ 当前时段看护临时移交，
        Agent 直接提醒被看护人本人，备份成员进入待命
```

## 4. 功能需求细化

### 4.1 模块一：家庭空间与成员角色

#### 4.1.1 空间与成员

- 一个家庭空间（`Space`）由创建者发起，其他人通过**家庭密钥**加入（见 4.1.2）。
- 每位成员加入时必须完成一次**授权确认**，明确同意：我与 Agent 的对话可被用于识别家庭事务，且每次进入家庭库前会再次征求我的同意。未完成授权的成员不产生任何家庭库数据。
- 成员有 `familyRole`（家庭称谓，本人选）、`role`（责任身份，见 2.1）和 `capacityState`（当前状态：正常 / 孕期 / 生病 / 出差 / 加班期 / 考试期）。

`capacityState` 是产品的价值观落点：**公平不是机械五五开。**报告和交接建议必须把当前状态作为输入，不能只看数量比例。

#### 4.1.2 家庭密钥：家庭功能的门（V1.2 修订，P0）

加入一个家的唯一通道是家庭密钥。不用手机号搜人，不用扫二维码加好友，不从通讯录推荐「你可能认识的家人」——**产品不主动发现家庭关系，只接受被邀请。**

**V1.2 的关键调整：密钥不是应用入口，而是家庭功能的门。**

打开应用不需要任何密钥。落地页就是一个通用 Agent 对话，可以改稿、查天气、随口聊，完整可用。只有当用户点进「家里」那一页时，才需要密钥。

```
打开应用
  ↓
通用 Agent 对话（完整可用，不需要密钥，不产生任何家庭记录）
  ↓ 用户主动点「家里」
密钥门：输入家里人私下给的密钥
  ↓ 服务端校验：限流 → 常量时间比对密钥哈希 → 解析出唯一一个有效绑定
进入家庭功能
  ↓
此后多出三样东西：
  · 全家的待办表，以及哪些事还没人管
  · 家庭群，Agent 在群里发提醒和报告
  · 1:1 对话里说的家里的事，会先问你要不要告诉家里人
```

**为什么这样改，而不是一进来就要密钥：**

1. **它让「采纳是渐进的」这个论点真正成立**（见 2.4）。老人可以先当豆包用几个星期，什么都不用配置。等家里人给了密钥，才多出家庭那一层。一上来就要密钥，等于把最大的分发优势堵死了。
2. **它把「通用 Agent 之上的家庭 Agent」变成了可以直接看见的产品结构**，而不是一句 slogan。没有家的时候家庭层根本不存在——不是隐藏，是不存在。
3. **它给隐私叙事提供了一个干净的演示**：同一句「奶奶下周要复查」，没进家时不产生任何记录，进家后才触发同意门。这一点比任何文案都有说服力。

**硬性规则（与 V1.1 相同）：**

1. **一个有效密钥只解析出一个家。**客户端永远不提供「你可能属于这几个家，挑一个」的选择器，也不猜测匹配。
2. 密钥是高熵、可撤销、可轮换的。服务端只存**带盐的密钥哈希**，比对使用常量时间算法。
3. 原始密钥**永不落日志、永不回传、永不存进浏览器或客户端**。匹配成功后立刻从输入框清除。
4. 无效、过期、已撤销、被限流四种情况返回**同一个错误响应**，避免通过错误信息枚举出「哪些家存在」。
5. 密钥交换成功后轮换会话；会话 Cookie 使用 `Secure` + `HttpOnly` + `SameSite=Lax` 或更严。
6. 退出登录只吊销本次会话，**不吊销密钥**。密钥轮换由家庭管理员单独操作。
7. 密钥只授予「进入这一个家」的权限。它**不授予**读取历史对话的权限，也**不自动授予任何身份**。

**硬性规则：**

1. **一个有效密钥只解析出一个家庭。**客户端永远不提供「你可能属于这几个家庭，挑一个」的选择器，也不猜测匹配。
2. 密钥是高熵、可撤销、可轮换的。服务端只存**带盐的密钥哈希**，比对使用常量时间算法。
3. 原始密钥**永不落日志、永不回传、永不存进浏览器或客户端**。匹配成功后立刻从输入框清除。
4. 无效、过期、已撤销、被限流四种情况返回**同一个错误响应**，避免通过错误信息枚举出「哪些家庭存在」。
5. 密钥交换成功后轮换会话；会话 Cookie 使用 `Secure` + `HttpOnly` + `SameSite=Lax` 或更严。
6. 退出登录只吊销本次会话，**不吊销密钥**。密钥轮换由家庭管理员单独操作。
7. 密钥只授予「进入这一个家」的权限。它**不授予**读取历史对话的权限，也**不授予任何成员身份**。进入后仍要走授权确认。

产品内文案必须说清：密钥是家人之间私下给的，像家门钥匙。丢了就找管理员换一把，换掉之后旧的立刻失效。

> 演示口径：Demo 使用**公开的固定演示码**，并在界面上明确标注「这是公开演示码，不是真实密钥」。不要让评委以为这就是生产认证。

#### 4.1.3 身份初始化：只选家庭称谓（V1.2 降为 P1）

> **这一版没有实现。**当前原型里称谓来自预置数据，用户没有选择步骤。保留在文档里是因为它是合理需求，只是排在 P0 之后。

进入家庭功能后的第一步应该是选身份。**这一步只做一件事：选一个家庭称谓。**

- 可选项：妈妈、爸爸、爷爷、奶奶、女儿、儿子、其他（自填两个字）。
- 每个称谓对应一个默认头像；也可以上传本地图片替换（PNG / JPEG / WebP，2 MB 以内，服务端需重新编码并剥离元数据，会话里只保留不透明的资源 ID）。
- 称谓可以随时改，改动不影响任何已有结论或责任归属。

**明确不做：**

- 不提供工作 / 职业 / 通勤 / 同事 等任何非家庭身份维度。**这个产品只有家庭场景，没有工作场景。**
- 不提供「职业形象」「上班形态」这类头像变体。它们不承载任何产品含义，只会让人以为存在一个工作空间。
- 不做细分角色（比如「长女」「二儿子」「外婆」还要再分）。称谓的用途是称呼和展示，分细了没有对应的产品行为，只增加填表负担。
- 不在这一步问 `primary/partner/subject`。责任身份由 2.1 的规则得出，用户看不到这套词。

#### 4.1.4 会话结构

**会话结构就是微信那一套：一个会话列表，用户自己点进哪个会话。**

| 会话类型 | `type` | 什么时候有 | 说明 |
| --- | --- | --- | --- |
| 我与 Agent 的 1:1 对话 | `agent_dm` | 一开始就有 | 主要输入面。内容默认**不进**家庭库，要过同意门 |
| 家庭群聊 | `family_group` | 进家之后才有 | 多人 + Agent，Agent 在此发提醒和报告 |

两者共用同一套会话 / 消息模型，用 `type` 区分。

**没进家之前，会话列表里只有一个「记得」**，它就是个通用助手，说什么都不会留下家庭记录。进家之后才多出家庭群，用户可以在两个会话之间切。

这个顺序很重要：它让家庭层的出现有一个用户能感知的时刻——**在他自己拿到密钥、自己点进去之后**，而不是注册时就悄悄开好了。

#### 4.1.5 责任身份从行为里推断（V1.1 新增，P0）

不问用户是什么身份，从对话内容和待办数据里推断。产品本来就在从对话里识别隐形劳动，那它也应该能识别出谁在承担、谁在被照护。

**推断信号：**

| 推断为 | 主要信号 |
| --- | --- |
| `primary` | 隐形劳动占比最高；`discoveredBy` / `scheduledBy` / `followedUpBy` 大量指向此人；拥有的责任域最多；无主责任域的下一步动作实际由此人在推进 |
| `partner` | 有 `executedBy` 记录但隐形劳动少；拥有的责任域为 0 或很少。这是默认态 |
| `subject` | 有指向此人的 `CareRule`；他人对话中此人作为被照护对象被提及；此人自己的对话里出现症状、用药、行动不便；此人几乎不出现在任何阶段字段里 |

**护栏，每一条都是硬性的：**

1. **推断结果只用来调整这个人自己的首页形态和提醒策略。**它服务于本人，不是给别人看的判断。
2. **推断出的身份不出现在界面上，对本人和对其他成员都一样。**

   - 不作为标签展示给其他成员：爸爸的界面上永远不会出现「奶奶：被看护人」。奶奶在别人眼里就是奶奶。
   - 也不告诉本人「系统判断你是主责任人」。产品的做法是**直接给她合适的首页**，而不是先给她贴一个标签再解释。
   - 禁用范围包括中文定性词。哪怕是在描述一条看护规则时，也不写「被看护人：周素兰」，而写「提醒谁：周素兰」——前者在给人定性，后者只是陈述事实。
   - 唯一可以出现的身份词是**家庭称谓**（妈妈、爸爸、奶奶……）。
3. **推断不改变可见性、不改变权限、不改变任何写入授权。**那些只由同意门和显式设置控制。推断错了最坏的后果是版式不合适，不会导致数据泄漏。
4. **本人的覆盖优先于推断。**首页常驻一个「这不是我的情况」入口，一次点击切换成另一种首页形态。覆盖之后推断不再改动它，覆盖动作写入 `AuditLog`。
5. **冷启动不猜。**数据不足时全员按 `partner` 处理，给中性的首页。宁可少给一个定制界面，不能一上来就把人归类。
6. **推断是渐变的，不是一次性打标。**它随数据持续更新。某个人这个月是 `primary`，交接成功后下个月可能不再是——这正是产品想看到的变化。
7. **`subject` 的推断额外多一道：只调整他/她自己的界面（大字号、语音优先、单一入口），不自动创建任何看护规则。**看护规则永远需要人明确说出来并确认激活（4.6.1）。

> 这条设计还有一个副作用：它让产品的核心主张自洽。产品的立论是「隐形劳动看不见，需要被识别出来」——如果连「谁是那个一直在记得的人」都要靠填表来问，那这个立论就不成立。

### 4.2 模块二：Agent 对话（输入面，不是首页）

**明确边界：聊天是输入面，不是产品中心。**首页分三张（见第 6 章），聊天只是老人侧的首页。

| 能力 | 要求 | 优先级 |
| --- | --- | --- |
| 文字对话 | 接大模型 API，具备正常的日常闲聊能力（老人侧的独立价值来源） | P0 |
| 结构化卡片消息 | 承载同意门询问、交接卡、提醒、报告、升级通知 | P0 |
| 语音输入 | 老人侧优先。MVP 可只做一条预置真实语音演示，其余用文本 | P1 |
| 图片 / 截图输入 | 医院通知、学校通知、缴费单的识别 | P1 |
| 手动转发补录 | 主责任人把外部消息粘贴进来补录 | P1 |
| 家庭群内提醒 | Agent 主动在群里发提醒与本周报告 | P0 |

**Agent 在群聊里的行为红线：**只发提醒、报告、交接卡。**不评价成员、不催促特定人、不代替某人向另一人表达不满、不自动发送任何指责性内容。**

### 4.3 模块三：见证与同意门（本产品的合规主干）

#### 4.3.1 见证：从对话中识别潜在责任

每一轮对话后，见证 Agent 判断这句话里是否存在潜在家庭事务，并产出 `Signal` 草稿：

- 这是不是一个潜在任务，还是只是闲聊 / 讨论
- 它属于哪个责任域
- 是一次性任务还是长期责任
- 谁发现了问题
- 是否有时间约束，是否明确
- 哪些信息还没确定
- 置信度

**只是讨论的内容不能直接创建任务。**置信度低于阈值的信号不打扰用户，只入待观察池。

#### 4.3.2 同意门：私聊到家庭库的唯一通道

> **这是整个产品最关键、也最容易做错的机制。**

**规则：`agent_dm` 的内容默认不进家庭共享库。**任何一条内容要升级为家庭事务，必须经过发言人本人显式确认。

流程：

```
奶奶在自己手机上：「腿又疼了」
        ↓
Agent（仅奶奶可见）：「要不要我把这件事告诉家里人？」
        ↓
   ┌──「告诉」→ 进入家庭库，标记「奶奶本人授权」
   ├──「先别说」→ 只留在奶奶这一侧，不进家庭库，不计入任何报告
   └──「只告诉女儿」→ 进入家庭库，visibility 限定为指定成员
```

**被看护人有权拒绝共享。**老人可以说「这件事别告诉我儿子」，系统必须遵守。这一条同时做到三件事：它是「边界 Agent」的具体落地；它把产品和伴侣监控 / 老人监控彻底区分开；它承认被照护者也是有主体性的人，而不只是被管理的对象。

家庭库条目的 `visibility` 取值：

| 值 | 含义 |
| --- | --- |
| `space` | 空间内全员可见 |
| `care_related` | 仅照护相关成员可见（用于健康信息） |
| `members:[...]` | 仅指定成员可见 |
| `self` | 仅本人可见，不进共享库 |

#### 4.3.3 没进家的时候，同意门根本不会出现

这是 V1.2 的一个结构性结果，值得单独说：**家庭层挂在「已进家」这个状态上。**

同一句「奶奶下周要复查，得挂骨科」：

| 状态 | 发生什么 |
| --- | --- |
| 还没进家 | 当作普通对话处理。**不产生任何记录，不出现同意门。**它就是个助手 |
| 已进家 | 产出一条仅本人可见的原始记录，然后弹同意门问她要不要告诉家里人 |
| 已进家但关掉了「帮我记着家里的事」 | 同「还没进家」。照样能聊，但不再往家里的记录里加东西 |

三条路径的差别不是文案差别，是**真的不产生数据**。这一点必须能在演示里当场验证：说一句话，然后去别人的界面上搜，搜不到。

### 4.4 模块四：责任域与隐形劳动度量

#### 4.4.1 责任域聚合

责任域 Agent 把零散信号合并成完整责任域。例如以下四条不是四个独立任务：

```
「妈最近腿又疼了」
「上次医生说一个月以后复查」
「要先挂哪个科？」
「报告放哪了」
```

它们同属一个责任域：**妈妈的近期健康照护**。

责任域字段：名称、`ownerId`（可为空）、状态、下一步动作、关联任务列表、关联证据列表。

**`ownerId` 为空本身就是产品要报告的结论**——「这个责任域目前没有主人」。

#### 4.4.2 五阶段归属（最关键的数据决策）

每个 `Task` 上必须显式记录五个阶段各由谁承担，**这五个字段是数据库一等字段，不允许靠事后统计推导**：

| 字段 | 对应阶段 |
| --- | --- |
| `discoveredBy` | 发现问题 |
| `deadlineKeptBy` | 记住截止时间 |
| `scheduledBy` | 制定安排 |
| `executedBy` | 实际执行 |
| `followedUpBy` | 跟进结果 |

每个字段可为空，可与其他字段指向不同成员。归属由 AI 从证据中推断出草稿，用户可在报告页一键修正（修正动作写入 `AuditLog`）。

> 如果这组字段在最后才补，那张责任集中度表就只能靠模型现场生成，评委追问细节必然崩。**这是排在最前面的实现项。**

#### 4.4.3 本周责任集中度报告

呈现形式（示例）：

| 工作阶段 | 妻子 | 丈夫 |
| --- | --- | --- |
| 发现问题 | 3 | 0 |
| 记住截止时间 | 3 | 0 |
| 制定安排 | 3 | 0 |
| 实际执行 | 2 | 1 |
| 跟进结果 | 3 | 0 |

指标定义：

| 指标 | 计算方式 |
| --- | --- |
| 隐形劳动占比 | （发现 + 记住 + 安排 + 跟进）在该成员全部承担项中的比例。执行是可见劳动，其余四项是隐形劳动 |
| 协调集中度 | 隐形劳动条目中，占比最高成员的份额 |
| 无主责任域数 | `ownerId` 为空的责任域数量 |
| 仅执行参与 | 执行占比高但责任域拥有数为 0 的成员 |

**叙述必须中性。**产品说：

> 本周家庭协调工作集中在一位成员身上。虽然执行任务有所分担，但发现、安排与跟进仍未形成完整责任所有权。

产品**不**说：「丈夫只做了 10%，他不合格。」

**禁止清单（硬性）：**不做懒惰排行榜、不做贡献积分榜、不做「最佳伴侣」评价、不做 AI 判定谁对谁错、不自动发送指责性消息、不做情绪诊断、不做关系质量评分、不从对话推测人格。

产品只呈现四件事：工作集中在哪里、哪些责任没有主人、哪些人只承担执行没有承担完整责任、怎样交接可以减少协调负担。

### 4.5 模块五：责任交接

#### 4.5.1 交接包内容

| 字段 | 说明 |
| --- | --- |
| 责任域说明 | 这一整块包含什么，边界在哪 |
| 历史记录 | 已经发生过什么（上次检查结果、上次是谁去的） |
| 关键约束 | 时间限制、预算、被照护人的偏好与禁忌 |
| 相关联系人 | 医生、老师、护工、亲属 |
| 已知信息 | 已确定的事实 |
| **未确定事项** | 必须补齐才能生效的空白项 |
| 下一步动作 | 接手后第一件要做的事 |
| 证据链 | 每一条结论对应的原始消息，可点击溯源 |

#### 4.5.2 交接状态机

```
draft → proposed → pending_info（信息不足）
                 → pending_ack（等接手人确认）
                 → accepted → active
                 → declined / expired

pending_info / pending_ack 期间统一对外呈现为 blocked
```

**硬性规则：**

1. **信息不完备或接手人未确认时，状态必须停在 blocked，所有权不转移。**绝不能出现「以为交出去了其实没人管」——责任不允许落到地上。
2. 交接需**双方确认**：提出方确认移交，接手方确认接收。
3. accepted 之后，该责任域的全部提醒改发给新主人。**原主责任人不再收到催办提醒**，其首页对应条目消失。
4. 交接记录不可删除（可归档），写入 `AuditLog`。

这一条规则继承 `finance-agent-lab` 的设计：**遇到未知或信息不足时默认阻断，绝不默认成功。**

### 4.6 模块六：看护与升级链路

#### 4.6.1 从自然语言到看护规则

AI 只负责一件事：从「奶奶血压药一天两次，饭后吃」这类句子里抽出 `CareRule` 草稿。抽完之后**必须由人确认才能激活**。

之后的定时、发提醒、等回应、超时判定、升级给谁、闭环记录，**全部是确定性程序，一行 LLM 都不能有。**

> 答辩要点：我们没有把所有东西都交给 Agent。有后果的部分交给状态机。

#### 4.6.2 CareRule 字段

| 字段 | 说明 |
| --- | --- |
| `subjectId` | 被看护人 |
| `title` | 如「血压药」「接孩子」 |
| `schedule` | 重复（每天 08:00 / 20:00）或一次性 |
| `requireAck` | 是否需要被看护人回应 |
| `ackTimeoutSec` | 回应超时阈值 |
| `escalationChain` | 有序升级链，每级含目标成员列表与延迟 |
| `primaryCaregiverId` | 主看护人 |
| `createdFromEvidenceId` | 由哪句话生成，可溯源 |
| `confirmedBy` | 确认激活的成员，为空则不激活 |
| `status` | `draft` / `active` / `paused` / `archived` |
| `announceTargets[]` | 可选的播报设备列表。为空即只走手机提醒。见 4.10 |

#### 4.6.3 CareEvent 状态机

```
scheduled → notified → acked → closed
                     → ack_timeout → escalated_L1 → escalated_L2 → ...
                                   → handled → closed
                                   → unresolved（留痕，不静默消失）
```

规则：

- 提醒优先发给**被看护人本人**（其手机 / Agent 对话页），而不是先发给看护人。这是这个功能的意义所在。
- `requireAck` 为真时，回应可以是一次点击（「吃了」）或一句语音，门槛必须极低。
- 升级链的最后一跳是**提醒家人去现场确认**，而不是让 App 自己承担判断责任。
- 每一次提醒、回应、超时、升级都写 `CareEvent`，报告页可回溯。
- **手机不是唯一出口。**老人可能没带手机、没看屏幕、或者压根没听见。`CareRule` 可以额外挂一个物理播报通道（机器人 / 音箱），与手机提醒**并行触发**，见 4.10。但播报**不改变**超时判定：播出去了不等于她听见了，`requireAck` 仍然只认她本人的回应。

#### 4.6.4 看护人临时不在

看护人可主动声明「我现在有急事，两小时内不在」：

1. 该时段内的看护规则临时移交，Agent 直接提醒被看护人本人
2. 备份成员进入待命状态，收到「本时段由你兜底」的通知
3. 时段结束后自动恢复
4. 全过程留痕

#### 4.6.5 安全边界（必须写入产品内文案）

- 本产品**不是医疗设备**，不提供诊断，不替代急救。
- 不做用药剂量建议、不做症状判断。
- 涉及自伤、家暴、急性医疗症状等高风险内容时，边界 Agent **不生成任务**，而是给出提示并建议联系专业资源（急救电话 / 专业机构），同时不做任何诊断性表述。

### 4.7 模块七：提醒与待办

| 能力 | 说明 | 优先级 |
| --- | --- | --- |
| 责任域提醒 | 发给责任域当前主人，不群发 | P0 |
| 看护提醒 | 见 4.6 | P0 |
| 群内本周报告 | 每周一次，中性叙述 | P0 |
| 待办列表 | 按责任域分组，不是平铺的任务清单 | P0 |
| 提醒去重 | 同一事项在 1:1 和群聊里不重复轰炸 | P0 |
| 物理播报 | 看护提醒可并行播报到指定设备，见 4.10 | P1 |
| 静默时段 | 每位成员可设免打扰时段（看护类高优提醒可穿透，需显式配置） | P1 |

**提醒的对象规则是产品主张的体现：**提醒只发给责任域的主人。系统不承担「帮 A 提醒 B」的角色——那正是要消灭的协调劳动。

**播报与手机提醒并行，不是二选一，也不叠加计数。**同一个 `CareEvent` 只有一次超时判定，播报成功与否都不影响它。

#### 待办的呈现口径（V1.2 修订）

原口径是「按责任域分组，不是平铺的任务清单」。V1.2 放宽为：

**可以按日期排成时间表，但每一条必须同时带着它属于哪一块责任、以及这一块归谁。**

理由是这两件事其实不冲突。用户真正需要「今天要干什么」这个视图，纯按责任域分组反而不好用。但如果一条待办脱离了责任归属单独出现，产品就退化成普通待办 App 了——那正是决策 #2 要避免的。

所以硬性要求是：

- 每条待办上必须可见：所属责任域的名字、这一块的主人（没有主人就标出来）。
- **「这周有哪些事一直只有你在记得」必须独立成块，且排在待办表之前。**这是产品的立论，不能混进日程里。
- 没有主人的责任域要单独成一节，不能只在待办行里用小字标注。

换句话说：时间表是**视图**，责任归属是**主轴**。视图可以换，主轴不能丢。

### 4.8 模块八：交接沟通助手（原「矛盾调解」的收敛形态）

原始设想是「家庭矛盾解决 AI 助手」。该形态与产品的三条红线（不做情绪诊断、不做关系评分、不做「AI 帮你教育伴侣」）直接冲突，且现场演示极易被质疑「凭什么 AI 判断我家谁对谁错」。

**收敛为一个动作，不是一个功能模块：**

- 只作用在**用户自己尚未发出**的那条消息上
- 提供一次「换个说法」：把指责性表达改写为「事实 + 我的需求 + 具体请求」
- 例：「你从来不管妈的事」→「妈下周三要复查，我这周排不开。你能不能接下这次的挂号和陪诊？」

**硬性约束：**不主动介入群聊、不评价对方、不生成给对方看的话术、不保存所谓「矛盾记录」、不做和解建议。

命名对外为「交接沟通助手」，不叫「矛盾调解」。

### 4.9 模块九：隐私、权限与数据控制

#### 4.9.1 三层数据分层（因接入大模型 API 而必须重新定义）

| 层 | 内容 | 存储 | 可见性 |
| --- | --- | --- | --- |
| L0 原始证据 | 聊天原文、语音、截图 | 端内 / 本地优先 | 仅本人 |
| L1 结论 | 信号、责任域、任务、交接、看护记录 | 家庭共享库 | 按 `visibility` 控制 |
| L2 模型输入 | 发给大模型的最小必要片段 | 不落第三方日志 | 脱敏后发送 |

L2 脱敏规则：真实姓名替换为角色代号（「妈妈」「老大」）、手机号 / 身份证 / 详细地址屏蔽或截断、只发送本轮判断所需的最小上下文窗口。

**不要绕这个问题。**对外表述就是：原始数据留在端内，发给模型的是最小必要且脱敏的片段，家庭库里存的是结论加证据指针。这个说法是诚实的，也仍然比同类产品克制。

#### 4.9.2 用户权利（每一项都要有 UI 入口，P0）

- 查看每一项结论来自哪一句原话（证据溯源）
- 删除单条证据（联动使相关结论失效或重算）
- 撤回授权（此后不再产生新信号）
- 导出自己的数据
- 关闭 AI 分析（保留纯聊天能力）
- 删除整个家庭空间（一键，二次确认）

#### 4.9.3 明确不做

不后台读取私人聊天、不监控位置、不自动读取个人日历、不分析未授权成员、不根据情绪推测人格或关系质量、不生成任何形式的伴侣评分。

### 4.10 模块十：机器人播报适配器（V1.1 新增）

#### 4.10.1 定位

一个放在客厅的机器人 / 智能音箱，作为看护提醒的**可选物理输出通道**。

它补的是一个真实缺口：4.6.3 要求「提醒优先发给被看护人本人」，但老人常常不看手机。有个东西能在客厅里出声说「素兰，该吃降压药了」，触达率比推送高一个量级。

**它不是什么，必须写死：**

- 不是身份提供者。机器人不知道谁是谁，站在它面前的人不构成任何身份凭据。
- 不运行产品的 Agent。它只播报已经成型的文本。
- 不拥有日程、责任域、同意状态、可见性策略、升级策略或完成状态。
- 不是完成证据来源。**播出去了不等于有人听见，更不等于有人做了。**

```
产品 outbox → 已通过授权与确认的播报意图 → 播报模块 → 播报端口
                                                    ├─ 假适配器（测试用）
                                                    └─ 硬件适配器（真机）
```

这个边界的价值：**没有硬件也能完整测试和演示整个产品**，硬件固件或网络一变，影响只锁在一个边缘适配器里。

#### 4.10.2 交付状态必须分成五种，不能只有成功和失败

这是本模块最重要的设计，它和决策 #7「绝不默认成功」是同一条原则：

| 状态 | 含义 |
| --- | --- |
| `delivered` | 观察到明确的播放完成信号 |
| `accepted_unverified` | 设备接受了请求，但**没有观察到任何播放中状态**。不能算送达 |
| `timed_out` | 超时。与失败分开记 |
| `cancelled` | 被更高优先级打断或主动停止 |
| `failed` | 明确失败，带稳定错误码与是否可重试 |

`accepted_unverified` 这一档是刻意加的。设备返回「已接受」通常只代表请求进了队列，不代表喇叭真的响过。把它算成送达就是在骗自己，也会让升级链在该升级的时候不升级。

**并且：以上五种状态里没有一种能证明「某个具体的人听到了、理解了、同意了、做完了」。**共享空间播报的受众是「一个被授权的物理位置」，不是一个人。所以：

- 播报**不能**满足 `requireAck`。超时判定只认被看护人本人的回应。
- 播报**不能**作为升级链的一跳来「代替」通知家人。它只是和手机提醒并行的一路输出。
- 升级链最后一跳仍然是「建议有人到现场确认」。

#### 4.10.3 文本与安全边界

- 播报文案走**白名单模板**，不允许自由生成。V1 三个模板：
  - `care_reminder`：「{称谓}，{事项}时间到了，{说明}」
  - `escalation`：「{称谓}的{事项}还没有回应，请家人查看」
  - `handover_confirm`：「{责任域}的交接已确认」
- 每个模板字段做长度与控制字符清洗，渲染后总长度受设备上限约束（按具体硬件文档定，超限直接拒绝而不是截断）。
- 播报默认**关闭**，由部署配置显式开启。
- 设备地址是部署配置，**永远不接受来自外部事件或用户输入的地址**。公网地址必须走 HTTPS；明文 HTTP 只允许私网或回环地址。
- 不提交任何设备凭据到仓库。如果固件需要认证，凭据放部署密钥管理。
- 同一时刻只播一条，播报在服务实例内串行化。跨实例的串行化由产品侧的持久 outbox 负责，不指望适配器。
- 日志与错误里**不出现**播报原文、设备响应体、被看护人姓名。
- **静默时段对播报的约束比推送更严**：夜间默认完全不播报，需要穿透必须逐条显式配置，因为半夜客厅突然出声会惊到老人。

#### 4.10.4 上线前的人工验证闸门

真机播报是会在物理空间里出声的动作，属于有后果的操作，所以采用 fail-closed：

1. 确认设备型号与固件版本，记录在案。
2. 确认操作机与设备在预期的私有网络内。
3. 确认此刻播报不会造成惊吓或误解（家里有人在休息就不测）。
4. 设置一个显式的「我确认要在真机上出声」环境变量，缺失则拒绝执行。
5. 先播一句正常优先级的短句，人工核对返回状态与实际听到的声音是否一致。
6. 断网重试一次，确认得到稳定的可重试错误码，且错误里不泄漏设备细节。

**肢体动作、转头、移动等一切非播报能力，V1 全部不做。**它们需要独立的运动安全评审，不在本模块范围内。

### 4.11 模块十一：连接中心（V1.2 新增）

#### 4.11.1 定位与口径修订

让 Agent 能在用户已经在用的聊天工具里工作，而不是要求全家搬到一个新 App 里。这是应用的第三个功能页。

> **这一节修订了 7.4 原来的「不做真实微信接入」。**V1.1 之前的口径过于笼统，把两件性质完全不同的事混在了一起：
>
> | 做 | 不做 |
> | --- | --- |
> | 用户**扫码授权自己的账号**，让 Agent 能在他自己的私聊里收发消息 | 通过**扫码 / 手机号 / 通讯录去发现谁是他的家人** |
>
> 前者是本人对自己账号的授权，和「不监控」原则不冲突。后者是产品主动发现家庭关系，那条红线不动——加入一个家的唯一通道仍然只有家庭密钥。

**V1 只做两个连接器**，其余一概不做：

| 连接器 | 范围 | 明确不含 |
| --- | --- | --- |
| **个人微信** | 通过官方插件绑定用户自己的账号，只接**已经配对的私聊** | **不含微信群**。不读历史聊天。不做群消息抓取 |
| **第三方机器人** | 别的机器人把消息标准化后送进签名 HTTPS 接口 | 不提供开放注册。不接受未签名请求 |

企业微信、飞书、钉钉这些企业侧连接器**不做**——这个产品只有家庭场景，没有工作场景（见 4.1.3 与 7.4）。

#### 4.11.2 硬性边界

1. **扫码只证明「你能登录这个账号」，不证明「你是这个家的成员」。**绑定之后仍然需要一次显式的产品内配对。身份和渠道是两件事。
2. **二维码与登录状态只留在插件侧**，产品这边只存一个不透明的引用。不存密码、不存 cookie、不存扫码图。
3. **不读历史聊天。**连接建立之前的消息一律不进入产品。这一点必须写在连接前的确认页上，不能只写在隐私政策里。
4. **明确否认的能力要在界面上显式标出。**个人微信卡片上「不含微信群」要以划掉的形式呈现——含糊带过等于默认支持。
5. **第三方机器人的签名**绑定时间戳、随机串、HTTP 方法、路径和请求体哈希。5 分钟时间窗 + 一次性随机串防重放。
6. **返回 202 只代表事件已经收下并落盘**，不代表送到人。送达、已读、真的做了，是三件不同的状态——与 4.10.2 播报状态是同一条原则。
7. **外部消息不能自己指定内部字段。**平台传进来的 payload 不允许选择成员 ID、责任身份、同意状态或任何授权字段。
8. **平台凭据只进部署密钥管理**，不进仓库、不进日志、不进前端。
9. 每个连接器**可独立撤销**，撤销即刻停止收发，且不影响其他连接器。

#### 4.11.3 统一的消息路径

不管消息从哪个平台进来，都走同一条路：

```
平台验签 → 绑定身份 → Agent 出草稿 → 可靠投递
（拒伪造重放）（不靠昵称猜人）（有后果的先确认）（送到和看到分开算）
```

**第二步是关键：不靠昵称、群名或手机号猜成员。**外部渠道进来的消息必须能映射到一个已配对的成员，映射不上就停住，不猜。

#### 4.11.4 这一版的实现边界

原型里这一页**只展示已经定好的接入边界**。没有配置任何真实平台凭据，也没有启动任何消息适配器。演示时要如实说明这一点，不能让评委以为已经接通了。

## 5. 技术设计

### 5.1 多 Agent 划分（按责任域划分，不按功能划分）

Agent 之间**只通过结构化任务契约协作**，不做成几个头像互相聊天。

| Agent | 完整责任 | 输入 | 输出 |
| --- | --- | --- | --- |
| **见证 Agent** | 从每一轮对话 / 语音 / 截图中识别潜在责任并保留原始证据 | 单个会话的消息 + 有限上下文 | `Signal` 草稿 + `Evidence` |
| **责任域 Agent** | 把零散信号聚合成完整责任域，维护五阶段归属；**推断成员的责任身份** | `Signal` 与 `Task` 集合 | `Domain` / `Task` + 阶段归属草稿 + 身份推断 |
| **交接 Agent** | 生成交接包，检查接手人是否已获得必要信息 | `Domain` + 成员状态 | `Handover` 包 + 未确定事项清单 |
| **边界 Agent** | 权限、同意、脱敏、高风险内容拦截 | 所有跨层写入请求 | 放行 / 拦截 / 降级为待确认 |

**边界 Agent 的权重最高**：它守的是「私聊 → 家庭库」这道门，是产品的合规主干。任何写入家庭库的动作都必须过它。

它还要守一道 V1.2 新增的门：**「没进家」这个状态**。用户还没用密钥进家时，见证 Agent 的产出一律丢弃，不落任何记录。这不是在界面上隐藏，是真的不产生数据（见 4.3.3）。

**责任身份推断归给责任域 Agent**，因为它本来就在维护五阶段归属，谁在承担看不见的活儿，数据就在它手里。推断结果只影响本人看到哪种版式，护栏见 4.1.5。

**看护升级不做成第五个 Agent，做成确定性服务。播报也不做成 Agent，做成边缘适配器。**理由分别见 4.6.1 和 4.10.1。

### 5.2 AI 与确定性程序的职责边界

| AI 负责（模糊性） | 程序负责（边界） |
| --- | --- |
| 这是不是一个潜在任务 | 截止时间的计算与触发 |
| 它属于哪个责任域 | 成员权限校验 |
| 一次性任务还是长期责任 | 是否经过授权 |
| 五阶段分别是谁 | 任务与交接的状态流转 |
| 哪些信息还没确定 | 提醒规则与去重 |
| 把要点抽成看护规则草稿 | 看护升级链的全部判定 |
| 改写一句话的表达方式 | 删除、导出、审计记录 |
| 这个人是不是在承担看不见的活儿（身份推断） | 密钥校验与「是否已进家」的判定 |
| — | 播报的交付状态判定与静默时段拦截 |
| — | 本人对身份推断的覆盖（覆盖后程序锁定，模型不再改动） |
| — | 外部渠道的验签、防重放与成员映射（映射不上就停住，不猜） |

一句话：**AI 处理模糊性，程序控制边界。**

### 5.3 大模型接入

- 抽象 `LLMProvider` 接口，支持 OpenAI 兼容协议，可切换 DeepSeek / 通义千问 / Kimi / 豆包等。老人场景建议主用国内模型（延迟与合规）。
- 所有结构化输出**必须过 JSON Schema 校验**。校验失败重试一次；二次失败**降级为「待人工确认」而不是猜测**，继承 blocked-by-default 原则。
- 提示词版本化（`promptVersion` 字段随结论一起落库），便于回溯某条结论是哪版提示词产出的。
- 每次调用记录 token 与耗时，Demo 现场需要可预测的响应时间。

### 5.4 数据模型

```
User           用户：id, createdAt, joinedFamilyAt(nullable)
                     ← joinedFamilyAt 为空 = 还没进家，此时不产生任何家庭数据
Space          家庭：id, name, createdBy, createdAt
                     ← V1.2：一个用户只属于一个家，所以业务表不再带 spaceId
SpaceKey       家庭密钥：id, keyHash（带盐）, createdBy, createdAt,
                     expiresAt, revokedAt, lastUsedAt
                     ← 永不存原始密钥。比对走常量时间
Conversation   会话：id, type(agent_dm|family_group), memberIds[], lastMessageAt
                     ← agent_dm 一开始就有；family_group 进家之后才有
Member         成员：id, userId,
                     familyRole(妈妈|爸爸|爷爷|奶奶|女儿|儿子|其他), familyRoleText,
                     avatarRef,
                     inferredRole(primary|partner|subject), inferredAt, inferredBasis,
                     roleOverride(nullable), overriddenAt,
                     capacityState, consentAt, consentScope
                     ← familyRole 用户自选，是界面上唯一的身份词
                       责任身份不存单值，拆成 inferredRole（推断，可变）
                       与 roleOverride（本人覆盖，优先）
                       有效身份 = roleOverride ?? inferredRole ?? 'partner'
Evidence       证据：id, conversationId,
                     sourceType(agent_dm|family_group|screenshot|voice|forward),
                     rawRef（端内指针）, speakerUserId, occurredAt, visibility
Signal         信号：id, text, candidateDomainId, confidence,
                     status(pending|confirmed|dismissed|evidence_missing),
                     evidenceIds[], promptVersion
Domain         责任域：id, name, ownerId(nullable), status, nextAction, visibility
Task           任务：id, domainId, title, dueAt, status,
                     discoveredBy, deadlineKeptBy, scheduledBy, executedBy, followedUpBy,
                     evidenceIds[]
Handover       交接：id, domainId, fromId, toId, packet(json), missingInfo[],
                     status(draft|pending_info|pending_ack|accepted|declined|expired),
                     fromConfirmedAt, toConfirmedAt
CareRule       看护规则：见 4.6.2，含 announceTargets[]（可选播报目标）
CareEvent      看护事件：id, careRuleId, state, notifiedAt, ackedAt,
                     escalationLevel, escalatedTo[], handledBy, closedAt
Announcer      播报设备：id, label（如「客厅」）, kind, endpointRef（部署配置引用）,
                     enabled, quietHours, createdBy
                     ← endpointRef 是配置键，不是地址本身
Announcement   播报记录：id, announcerId, ruleId, careEventId, template, renderedLen,
                     state(queued|delivered|accepted_unverified|timed_out|cancelled|failed),
                     errorCode, startedAt, settledAt
                     ← 不存播报原文，只存模板名与长度
Channel        连接器：id, kind(personal_wechat|third_party_bot), state,
                     bindingRef（插件侧的不透明引用）, connectedAt, revokedAt
                     ← V1.2 新增。不存密码、不存 cookie、不存扫码图
AuditLog       审计：id, actorId, action, targetType, targetId, before, after, at
```

关键约定：

- `Evidence.rawRef` 指向端内存储，家庭库只存指针和最小摘要。
- `Task` 的五个阶段字段是一等字段，不允许由视图层推导。
- `Handover` 的两个确认时间戳缺一不可，都非空才能进 `accepted`。
- 删除 `Evidence` 时必须联动处理引用它的 `Signal` / `Task`（标记为证据缺失并重算），不能留下无证据的结论。
- **`User.joinedFamilyAt` 为空时，见证 Agent 的产出一律丢弃。**不写 `Evidence`、不写 `Signal`、不弹同意门。这是 V1.2 的核心约束：没进家就真的不产生家庭数据，不是在界面上隐藏。
- **有效责任身份 = `roleOverride ?? inferredRole ?? 'partner'`。**本人覆盖永远优先，覆盖之后模型不再改动。冷启动时两者都为空，落到 `partner`——不猜。
- `inferredBasis` 要存下推断依据的摘要（哪些阶段字段、哪些看护规则），因为界面上要能回答用户「凭什么这么判断我」。
- `Announcement` 只记状态和错误码，**不记播报文本、不记设备响应体、不记被看护人姓名**。`queued` 是中间态，不算交付结果。
- `SpaceKey.keyHash` 使用带盐哈希，比对走常量时间。原始密钥不进任何表、不进任何日志。
- `Channel.bindingRef` 是插件侧的不透明引用。**产品这边不持有任何可用于登录的凭据。**

## 6. UI 设计原则

### 6.1 三张首页（核心设计决策）

同一个数据库，三张脸。

> 下表的「责任身份」一列是**文档术语**，用于说明机制。它不出现在界面上，见 6.5。

| 责任身份（文档术语） | 界面上叫 | 首页内容 | 为什么 |
| --- | --- | --- | --- |
| `primary` | 责任地图 | 责任地图 + 首屏一句话：**「这周，有哪些事一直只有你在记得？」** | 她要的是卸下负担，不是多一个聊天框 |
| `partner` | 我负责的 | 我负责的责任域 + 待确认的交接 | 他要的是明确知道哪一整块归我 |
| `subject` | 就是对话，没有名字 | 大字号、语音优先、只有一个输入框 | 她要的是一个能说话的对象，不需要理解产品概念 |

**承担最多的那个人，首页不是聊天界面。**这一条与「全家人都用 Agent 聊天」不冲突：聊天是输入面，责任地图是产出面。产品不要求所有人理解同一套概念。

**三条补充：**

1. **这三张脸不是用户选的，是推断出来的**（4.1.5）。用户从没被问过「你是不是家里最累的那个」，产品从对话和待办里看出来，然后给她对应的版式。
2. **每张版式都常驻一个「这不是我的情况」入口**，一次点击换成另一种。推断错了的代价必须是一次点击，不是找不到出路。
3. **V1.2：这三张脸只在「已进家」之后才存在。**没进家时应用只有一个通用对话页，没有版式之分。家庭功能是叠加上去的一层，不是默认打开的（见 4.1.2）。

#### 应用只有三个功能页（V1.2）

| 页 | 内容 | 没进家时 |
| --- | --- | --- |
| 对话 | 落地页。1:1 通用助手，进家后多出家庭群 | 完整可用，只有 1:1 |
| 家里 | 三张版式之一 | 显示密钥门 |
| 连接 | 连接中心（4.11） | 可用，但连上也没有家庭事件可转发 |

**「我的」不单独占一个页。**那些内容（原话溯源、家庭层开关、退出解散）放在导航栏右上角。理由是它们是低频操作，占一个主标签会挤掉更该被看到的东西。

界面上**永远不出现**责任身份，无论英文枚举还是中文说法，也不出现「系统判断你是主责任人」这类表述。用户看到的只有自己的家庭称谓和一个合适的首页。责任身份是内部模型，不是用户需要理解的概念，更不是贴在别人身上的标签。完整禁用词表与替代说法见 6.5。

### 6.2 老人与小孩侧的无障碍硬性要求

> 这一节说的是「就是对话」那张首页。「被看护人」是文档术语，界面上不出现，见 6.5。

| 项 | 要求 |
| --- | --- |
| 正文字号 | ≥ 20px，标题 ≥ 26px，支持系统字号放大 |
| 正文对比度 | ≥ 7:1（WCAG AAA），不依赖浅灰文字 |
| 点击区 | ≥ 60×60px（高于常规 44px 标准） |
| 回应操作 | 一次点击完成，或一句语音，不需要打字 |
| 界面元素 | 单屏功能不超过 3 个，无嵌套导航 |
| 颜色 | 信息不能只靠颜色承载，必须有文字或图标 |
| 动效 | 支持 `prefers-reduced-motion`，默认弱动效 |

### 6.3 报告与交接卡的表达规范

- 数字用于呈现分布，不用于打分。不出现总分、等级、排名。
- 责任集中度表用中性色，**不给任何成员标红**。
- 交接卡上的「未确定事项」必须视觉突出，因为它是 blocked 的原因。
- 每条结论旁有证据入口（一个可点的来源标记），点开是原话。

### 6.4 视觉风格

**待定稿。**方向建议：低饱和、暖中性、克制。这是一个处理家庭健康与关系的产品，不应使用游戏化或竞技感的视觉语言（仓库内社交产品那套「亮黄 + 黑描边 + 硬投影」的玩具箱风格**不适用于本产品**，不要复用）。

需在开发启动前定稿并落地 `:root` CSS 变量，避免样式散落后返工。

### 6.5 界面文案规范：责任身份不上界面（V1.1 新增）

再说一次这条分界，因为它极易被违反：**本文档用来把机制说准的术语，不等于可以出现在界面上的文案。**

#### 禁用词表

界面上（包括按钮、标题、字段名、空态、提示、Toast、设置项、演示用的辅助标注）不出现下列任何一个词：

| 禁用 | 为什么 | 界面上改成 |
| --- | --- | --- |
| `primary` / `partner` / `subject` | 内部枚举，用户无需理解产品的责任模型 | 不出现。用**家庭称谓**（妈妈、爸爸、奶奶） |
| 主责任人 | 等于告诉用户「系统认定你最累」。产品该做的是直接给她合适的首页，不是先贴标签再解释 | 不出现 |
| 被看护人 | 在给人定性，把她说成被管理的对象，直接违反 4.3.2 | 描述看护规则时写「提醒谁」 |
| 共同生活成员 | 同上，且是一个没人会自称的词 | 不出现 |
| 责任身份 / 角色分层 | 暴露内部模型 | 不出现。要描述就描述用户看到什么，比如「首页是责任地图」 |
| capacityState | 字段名 | 「我最近的状态」 |

#### 允许且鼓励的说法

- **家庭称谓**：妈妈、爸爸、爷爷、奶奶、女儿、儿子、其他。这是界面上唯一的身份词。
- **描述用户看到什么，而不是他被归为什么**：「首页是责任地图」「首页是我负责的」「首页就是对话」。
- **陈述事实而非定性**：「提醒 周素兰」而不是「被看护人 周素兰」；「我在家里是 妈妈」而不是「角色：primary」。

#### 三张首页怎么在界面上区分

它们的差别通过**内容**体现，不通过标签体现。用户打开就看到对自己合适的那张，界面从不解释「你之所以看到这张是因为你是 X」：

| 看到什么 | 界面上叫它 |
| --- | --- |
| 责任地图 + 「这周，有哪些事一直只有你在记得？」 | 责任地图 |
| 我负责的责任域 + 待确认的交接 | 我负责的 |
| 大字号单一对话 | 就是对话，没有名字 |

#### 怎么保证不违反

把禁用词表写成一条自动检查：渲染后扫描界面可见文本，命中任意禁用词即失败。这比靠人工评审可靠，因为抽屉、空态、Toast 这些默认不显示的地方最容易漏。检查要覆盖各个交互状态，不能只扫首屏。

## 7. MVP 范围（96 小时）

### 7.1 只做这一条链路

不做完整家庭管理平台。只支持：

| 项 | 规格 |
| --- | --- |
| 家庭 | **1 个**。一个用户只属于一个家 |
| 落地体验 | 打开就是通用助手，不需要密钥。点「家里」才要密钥（Demo 用公开演示码） |
| 成员 | 3 个账号，覆盖三种版式：责任地图 / 我负责的 / 只要一个对话框 |
| 家庭称谓 | 6 个预置称谓 + 「其他」。**不做职业维度**。选择步骤 P1 |
| 会话 | 每人一个 1:1 Agent 对话 + 进家后一个家庭群 |
| 责任域 | 3 个，其中 1 个没有主人 |
| 待办 | 按日期排的时间表，每条带责任域归属与主人 |
| 交接 | 1 次完整交接，**必须包含交不过去的状态和双方确认** |
| 看护 | 1 条完整升级链（提醒 → 无回应 → 往下找人 → 闭环） |
| 报告 | 1 份本周责任集中度报告（含五阶段表） |
| 隐私 | 同意门（含「只告诉某人」）+ 原话溯源 + 单条删除 + 退出解散 |
| 身份 | 由推断得出（不询问）+ 「这不是我的情况」一键覆盖 |
| 连接中心 | 2 个连接器：个人微信私聊 + 第三方机器人。只展示接入边界，不接真平台 |
| 沟通助手 | 「换个说法」单个按钮 |
| 播报 | **P1**。有硬件就演真机一句，没硬件就演假适配器 + 五种交付状态 |

**演示速度开关：**把看护超时从 30 分钟压成 60 秒，把「本周」压成可手动触发。否则现场无法演示。

### 7.2 P0 清单（缺一项 Demo 不成立）

1. `Task` 的五阶段归属字段落库（**排第一，最先做**）
2. 通用 Agent 对话可独立使用 + **「是否已进家」这个闸门**：没进家时见证产出一律丢弃
3. 家庭密钥门 + 授权流程
4. 会话列表 + Agent 1:1 + 进家后的家庭群，接通大模型 API
5. 见证 Agent：从对话产出 `Signal` + `Evidence`
6. 同意门：私聊内容进入家庭库前的本人确认，含「只告诉某人」
7. 责任域聚合 + 责任集中度报告（中性叙述）
8. **责任身份推断** + 本人一键覆盖（决定三张版式给谁看哪张）
9. 交接包生成 + 交不过去的状态 + 双方确认 + 提醒转移
10. 看护规则人工确认激活 + 确定性升级状态机 + 事件留痕
11. 原话溯源 + 单条删除 + 退出解散
12. 三张版式 + 「这不是我的情况」
13. **界面禁用词自动检查**（6.5）：扫描各交互状态下的可见文本，命中责任身份定性词即失败

第 2、8、13 项要特别说明：

- **第 2 项是 V1.2 的地基。**「没进家就不产生家庭数据」不是 UI 层的隐藏，是数据层的闸门。它必须在见证 Agent 之前就位，否则后面每条写入路径都要单独补判断。
- 第 8 项依赖第 1 项（五阶段字段）和第 7 项（集中度统计），所以排在它们之后。推断逻辑本身不复杂——数据都在手里，主要是把护栏做对。
- 第 13 项几乎零成本，但必须做成自动检查。抽屉、空态、Toast 这些默认不渲染的地方最容易漏，人工评审抓不住。

**连接中心（4.11）不在 P0。**它是路演里很有说服力的一页，但只需要把接入边界展示清楚，不需要真接平台。

### 7.3 P1（时间允许）

- 语音输入（真实 ASR）
- 截图转结构化记录
- 「换个说法」沟通助手
- 看护人临时不在的时段移交
- 静默时段
- `capacityState` 参与交接建议的权重
- **机器人播报适配器**：假适配器 + 五种交付状态必做，真机播报取决于硬件是否到位
- **连接中心**：展示接入边界即可，不接真平台（4.11）
- **加入时选家庭称谓**（4.1.3）。当前称谓来自预置数据
- 建家的完整流程（起名 → 生成密钥 → 分享给家人）。Demo 用预置的家顶过去

### 7.4 明确不做

不做支付、不做家庭成员定位、不做情绪诊断、不做情侣关系评分、不做复杂社交、不做十种家庭类型、不做万能聊天框、不做「AI 帮你教育伴侣」、不做外部照护者角色、不做诊断或用药建议。

**V1.2 修订（与 V1.1 相比）：**

| 变动 | 说明 |
| --- | --- |
| **移出** | 「**不做多家庭空间**」——V1.1 曾把它提到 V1，V1.2 又收回。现在 V1 只做单家庭，多空间退回第 13 章 V2 |
| **改写** | 原「**不做真实微信接入**」口径太笼统，把两件事混在一起了。现在拆开：**做**用户扫码授权自己的账号（4.11）；**不做**通过扫码 / 手机号 / 通讯录去发现谁是他的家人 |
| 新增 | **不做微信群**。个人微信连接器只接已配对的私聊，界面上要以划掉的形式明确标出 |
| 新增 | **不做企业侧连接器**（企业微信 / 飞书 / 钉钉）。这个产品只有家庭场景 |
| 新增 | **不读连接建立之前的历史聊天** |
| 保留（V1.1 起） | **不做工作 / 职业场景**。没有工作空间、没有工作身份、没有职业形象 |
| 保留（V1.1 起） | **不做通过手机号 / 通讯录 / 二维码发现家人**。加入一个家的唯一通道是家庭密钥 |
| 保留（V1.1 起） | **不做机器人的肢体动作**（转头、移动、手势）。只播报 |
| 保留（V1.1 起） | **不把播报当送达证据**。播报状态永远不能满足 `requireAck` |
| 新增 | **不把「返回 202」当送达证据**。网关收下事件 ≠ 送到人。与上一条同源 |

> 「不做真实微信接入」这条口径是整份文档里唯一被**放宽**过的红线，所以特别说明理由：
> 用户授权自己的账号，和产品去发现用户的社会关系，性质完全不同。前者用户是主体，后者用户是对象。
> 这个产品的红线一直是后者——不主动发现家庭关系、不读没授权的内容。放宽前者不动这条红线。

## 8. Demo 脚本

按此顺序演示，情绪曲线最好。全程约 4 分钟。

演示用一部手机，角色在演示台上切换（妈妈 / 爸爸 / 奶奶）。不要同时摆三台手机，看的人分不清在看谁。

| # | 画面 | 讲什么 |
| --- | --- | --- |
| 1 | 打开就是对话。改周报、问晚饭吃什么 | 「现在它就是个豆包。」这一步的作用是建立基线——**这些话不产生任何家庭记录** |
| 2 | 点「家里」→ 要密钥 | 加入一个家只有这条路：家里人私下给你密钥。我们不搜手机号、不读通讯录 |
| 3 | 输入密钥 → 进家。出现全家待办表、没人管的责任、以及「这周只有你在记得 7 件」 | 家庭层是**叠加**上来的一层，不是默认打开的。这一步之后产品才变成《都记得》 |
| 4 | 回到对话页，现在多了一个家庭群 | 同一个入口多了一个会话。Agent 会在群里发提醒和报告，但不评价任何人 |
| 5 | 切到奶奶。她说「腿又疼了」，Agent 问「要不要告诉家里人？」 | 一次演完两件事：同意门（不是偷偷记录）+ 老人侧的独立价值。**三个选项都值得试**，选「先别说」之后切回妈妈，那句话真的不存在 |
| 6 | 切回妈妈，弹出本周责任集中度表 | 念中性叙述那句。不指责任何人。表里每个数字都能当场追问 |
| 7 | 提议把「奶奶这次复查」整块交给爸爸 → **缺两项信息，交不过去** | **这一秒千万别跳。**全场最有工程说服力的地方：信息不足就阻断，责任不会不了了之 |
| 8 | 补齐信息 → 切到爸爸，他确认接下来 | 两边缺一个都不算交完。这里要强调「双方确认」不是走形式 |
| 9 | 吃药场景：爸爸临时有事 → 直接提醒奶奶本人 + 客厅播报 → 超时没回 → 往下找人 → 闭环 | 两句话必须说：这一段没有一行 AI；**播报回执显示「已接受但没看到播放」，所以超时该找人还是找**——播了不等于她听见了 |
| 10 | 连接中心 | 让 Agent 在常用聊天工具里工作。指着个人微信卡片上划掉的「不含微信群」说：我们不含糊这一点 |
| 11 | 回到「家里」：「只有你在记得」从 7 件变成 2 件。顺手点「这不是我的情况」 | 情绪落点。收尾补一句：这个版式不是她选的，是产品从她平时操心的事里看出来的；看错了一次点击就能换 |

全程约 4 分半。

**砍的顺序**（如果时间紧）：第 4 步可以并进第 3 步；第 10 步可以压成一张截图。**第 1、3、7、9、11 步不能砍**——它们分别承载「先是普通助手」「家庭层是叠加的」「交不过去」「播报不等于送达」「负担真的减少了」这五个论点，每一个都对应一类必然会被问到的追问。

第 1 步和第 3 步的对比是这一版新增的，也是最容易被低估的一段。它把「通用 Agent 之上的家庭 Agent」从一句 slogan 变成了可以当场验证的事实：同一句「奶奶下周要复查」，第 1 步说了什么都不留，第 3 步之后说才会问你要不要告诉家里人。

第 11 步末尾那句关于「身份是推断出来的」很值得讲，因为它直接回应评委最可能问的问题：凭什么产品知道谁累。答案是凭五阶段字段，那些数据在第 6 步就摆在台面上了。

机器人不在场时的降级演示：用假适配器跑同一条链路，把五种交付状态打在屏幕上，重点讲 `accepted_unverified` 为什么必须单独一档。**不要用一段预录的音频假装真机播报。**

**演示数据要求：**家庭群 Fixture 必须虚构但极其真实，第一眼看不出是设计过的。至少 3 个责任域、8 条以上有效信号、其中要包含 2 条「只是讨论不能建任务」的干扰句（用来展示见证 Agent 的判断力）。

## 9. 答辩预案

| 可能的追问 | 回答 |
| --- | --- |
| **凭什么全家人愿意都换到你们的 Agent 聊天？** | 不要求搬家。Agent 主要活在每个人自己的 1:1 对话里，老人侧是直接替代豆包的日常使用，本身就有价值。家庭事务的沉淀是 1:1 对话的自然副产品，不需要全家换群。不愿意换的成员，主责任人可以手动转发和截图补录。采纳是渐进的，不是全有或全无 |
| **这和普通待办 App 有什么区别？** | 普通待办把「陪妈妈复查」变成一条任务，完成即结束。我们把它变成一个有主人的责任域，包含发现、比较、预约、提醒、存报告、两周后复诊。交接的是整块，不是一次执行。区别不在功能，在交接的粒度 |
| **这不就是伴侣监控 / 老人监控？** | 数据只来自本人主动说给 Agent 的内容，且每一条进入家庭库前都要本人同意。被看护人可以拒绝共享，可以指定只告诉某个人。我们不读后台聊天、不读位置、不读个人日历 |
| **接了大模型 API，隐私怎么说？** | 分三层：原始证据留端内，发给模型的是脱敏后的最小必要片段，家庭库存的是结论加证据指针。每条结论都能点开看原话，也能单条删除 |
| **AI 判断错了怎么办？** | 三道防线：低置信度不打扰；所有归属和规则都可一键修正；信息不足或未确认时状态停在 blocked，绝不默认成功。看护升级链完全没有 LLM |
| **凭什么 AI 有资格判断我家谁对谁错？** | 它不判断。产品只呈现工作集中在哪里、哪些责任没有主人。没有评分、没有排行榜、没有对错结论。公平也不是机械五五开——孕期、生病、加班期都是系统的输入 |
| **多 Agent 是不是噱头？** | 四个 Agent 按责任域划分而非功能划分，只通过结构化契约协作。而且我们刻意**没有**把所有东西交给 Agent：有后果的部分交给状态机 |
| **一个人往往同时扛着两个家（爸妈家和自己的小家），你们只支持一个？** | V1 只做一个，这是刻意的取舍。多空间会带来一个新的头号风险：两个家的信息串台。「妈最近腿疼」出现在伴侣家的界面上，产品的全部信任叙事当场崩塌。我们不想在 96 小时里同时赌这个。它在 V2 路线里（第 13 章），而且做法已经想清楚了：会话归属哪个家，说话时就已经决定了，不需要问用户也不需要模型猜 |
| **为什么打开应用不需要密钥？不怕没人用家庭功能吗？** | 恰恰相反，这是为了让人用得上。老人可以先把它当豆包用几个星期，什么都不用配置——这是我们唯一现实的分发路径。一上来就要密钥等于把这条路堵死。而且这个顺序还有一个好处：家庭层的出现有一个用户能感知的时刻，是他自己拿到密钥、自己点进去的，不是注册时就悄悄开好的 |
| **接了微信，不就是读人家聊天记录吗？** | 两件事要分开。我们做的是**用户扫码授权他自己的账号**，让 Agent 能在他自己的私聊里收发消息；我们不做的是**通过扫码或通讯录去发现谁是他的家人**。前者用户是主体，后者用户是对象。加入一个家的唯一通道仍然只有家庭密钥。而且不含微信群、不读连接之前的历史聊天——这两条在界面上是明写的，个人微信那张卡上「不含微信群」是划掉的红字 |
| **为什么不让用户直接选自己是主责任人还是执行者？** | 因为这个问题答不上来。真正的主责任人往往不觉得自己在承担额外劳动——这恰恰就是隐形劳动的定义。所以我们不问，从数据里推断：五阶段字段已经记录了谁在发现、谁在记时间、谁在安排、谁在跟进，谁是主责任人是这些数据的自然结论。反过来说，如果连「谁一直在记得」都要靠填表来问，我们「隐形劳动需要被识别出来」的立论就不成立了 |
| **推断错了怎么办？把老人判成被看护人不是很冒犯？** | 三条护栏。第一，推断结果只影响这个人**自己**的首页形态，绝不作为标签展示给其他成员——爸爸的界面上永远不会出现「奶奶：被看护人」。第二，它不改变任何可见性和权限，推断错了最坏的后果是首页布局不合适，不会导致数据泄漏。第三，每张首页常驻「这不是我的情况」，一次点击换形态，本人的覆盖永远优先于模型。而且数据不足时我们不猜，全员给中性首页 |
| **加个机器人是不是硬件噱头？** | 它解决一个具体问题：老人不看手机。但我们把它限定得很死——它不运行 Agent、不拥有任何状态、默认关闭、只播白名单模板。最关键的是它**不能**作为送达证据：播报状态有五种，其中「设备已接受但没观察到播放」单独算一档，因为设备返回接受只代表请求进了队列。播了不等于听见了，所以超时判定只认被看护人本人的回应 |
| **播报会不会变成对老人的骚扰？** | 夜间默认完全不播，要穿透必须逐条显式配置。播报和手机提醒并行，不叠加、不重复轰炸。而且它播的是白名单模板，不是模型自由生成的话 |

## 10. 关键决策记录

| # | 议题 | 结论 | 依据 |
| --- | --- | --- | --- |
| 1 | 数据从哪来 | **全家人直接和 Agent 聊天，Agent 即入口。**放弃「导入群聊导出内容」作为主通道，保留手动转发 / 截图作为补录 | 群聊导出在真实世界不成立，且与「不监控」原则冲突。Agent 入口让数据流式化、授权天然化，并给出老人侧的分发理由 |
| 2 | 聊天是不是首页 | **不是。**聊天是输入面，首页分三张；只有老人侧的首页是聊天 | 一旦聊天成为产品中心，产品退化成「豆包 + 家庭群 + 待办提醒」，记忆点消失，且在助手赛道打不过大厂 |
| 3 | 家庭矛盾调解 AI | **降级为「换个说法」单个动作**，只作用于用户自己未发出的消息 | 原形态与「不做情绪诊断 / 不做关系评分 / 不做 AI 教育伴侣」三条红线冲突，且现场易被质疑越界 |
| 4 | 私聊内容能否直接进家庭库 | **不能。默认不进，必须本人显式同意**，并支持「只告诉某人」和被看护人拒绝共享 | 这是本产品与伴侣监控 / 老人监控的唯一分界线，也是「边界 Agent」的落地形态 |
| 5 | 看护升级链由谁执行 | **确定性状态机，无 LLM。**AI 只负责把自然语言抽成规则草稿，且必须人工确认才激活 | 照护有真实后果，不能交给概率模型。继承 finance-agent-lab 的 blocked-by-default |
| 6 | 五阶段归属怎么实现 | **数据库一等字段，不允许事后推导** | 责任集中度表是 Demo 的核心，靠模型现场生成会在追问下崩塌 |
| 7 | 交接信息不全怎么办 | **状态停在 blocked，所有权不转移** | 绝不允许「以为交出去了其实没人管」，责任不能落到地上 |
| 8 | 隐私叙事 | 从「全部本地」调整为**三层分层**：L0 端内 / L1 家庭库结论 / L2 脱敏最小片段 | 接了大模型 API 后「全部本地」不再成立，诚实分层比含糊承诺更可信 |
| 9 | MVP 成员数 | 从 2 人放宽到 **3 个角色 3 个账号** | 看护场景必须有被看护人这个第三方 |
| 10 | 视觉风格 | **不复用仓库内社交产品的玩具箱风格**，方向定为低饱和暖中性，具体待定稿 | 处理家庭健康与关系的产品不应使用游戏化 / 竞技感视觉语言 |
| 11 | 是否做第五个「看护 Agent」 | **不做**，做成确定性服务 | 同 #5。而且「刻意不把一切交给 Agent」本身是答辩加分项 |
| 12 | 怎么加入一个家庭空间 | **家庭密钥**，由家庭管理员私下给。一个有效密钥只解析出一个家庭，客户端不提供多家庭选择器，不猜测匹配 | 手机号搜人、通讯录推荐、扫码加好友都等于「产品主动发现家庭关系」，与「不监控」原则冲突。密钥的心智模型是家门钥匙：家人给的，丢了就换 |
| 13 | 用户选身份时选什么 | **只选家庭称谓**（妈妈/爸爸/爷爷/奶奶/女儿/儿子/其他）。删除职业与工作身份维度 | 职业维度是纯粹的范围外内容：这个产品只有家庭场景。称谓的用途是称呼和展示，分细了没有对应的产品行为 |
| 14 | 责任身份怎么确定 | **不问用户，从对话与待办中推断**，本人可一键覆盖且覆盖优先。推断结果只影响本人首页形态，**绝不作为标签展示给其他成员**，也不改变任何可见性与权限 | 三个原因。一是问不出来：真正的主责任人往往不觉得自己在承担额外劳动，这就是隐形劳动的定义，让她自评等于问了个答不上的问题。二是数据本来就在手里——五阶段字段已经记录了谁在发现、谁在记时间、谁在安排，推断谁是主责任人是这些数据的自然结论。三是绝不能让称谓推导身份，否则产品变成「按年龄把人归类为被管理对象」，违反 4.3.2。还有一层：如果连「谁一直在记得」都要靠填表来问，产品「隐形劳动需要被识别出来」的立论就不成立了 |
| 15 | 一个人能不能属于多个家庭 | **V1.1 曾定为「能，上限 5 个」，V1.2 收回：V1 只做一个家。**多空间退回第 13 章 V2 | 收回的理由不是不重要，是风险收益不划算。多空间会引入一条新的头号风险——两个家的信息串台，而这条风险一旦在演示现场发生，杀伤力比任何功能缺失都大。96 小时里不值得同时赌它。做法本身已经想清楚了（会话归属哪个家，说话时就决定了），V2 接着做的成本不高。附带收益：删掉多空间后，`spaceId` 不再需要贯穿所有表，P0 少了两项 |
| 16 | 责任身份要不要露在界面上 | **完全不露。**英文枚举和「主责任人 / 被看护人 / 共同生活成员」这些中文说法一律不进 UI，连演示用的辅助标注也不写。界面上唯一的身份词是家庭称谓。三张首页靠内容区分，不靠标签 | 两条理由。一是给人定性会造成真实伤害：把一个人标成「被看护人」等于告诉全家她是被管理的对象，违反 4.3.2；告诉某人「系统认定你最累」也不是她想要的，她想要的是负担变少。二是没有必要：用户不需要理解产品的责任模型就能用，直接给她合适的首页就行。附带好处是界面文案简单了很多。落地靠 6.5 的禁用词表 + P0 第 14 项的自动检查，不靠人工评审 |
| 17 | 机器人播报的定位 | **可选的物理输出通道**，与手机提醒并行。默认关闭、只播白名单模板、不运行 Agent、不拥有任何状态。交付状态分五种，「已接受但未观察到播放」单独一档，且**任何一种都不能满足 `requireAck`** | 老人不看手机是真实缺口，播报能提高触达。但共享空间播报的受众是一个物理位置而不是一个人，把它当送达证据就是在骗自己，还会让升级链在该升级时不升级。这一条与决策 #7「绝不默认成功」是同一原则 |
| 18 | 密钥放在哪一步 | **不是应用入口，而是「家里」这一页的门。**打开应用就能完整使用通用助手，不需要任何密钥。没进家时见证 Agent 的产出一律丢弃，不落任何记录 | 三个理由。一是它让「采纳是渐进的」（2.4）真正成立——老人可以先当豆包用，这是唯一现实的分发路径。二是它把「通用 Agent 之上的家庭 Agent」变成看得见的产品结构：没有家的时候家庭层不是隐藏，是不存在。三是它给隐私叙事提供了一个能当场验证的对比：同一句话，进家前什么都不留，进家后才问你要不要告诉家里人 |
| 19 | 要不要接微信 | **接，但只接用户自己的账号授权，且只接已配对的私聊。**不含微信群、不读历史聊天、不做通过扫码或通讯录发现家人。这修订了 V1.1 之前「不做真实微信接入」的口径 | 原口径把两件性质不同的事混成了一条：用户授权自己的账号（用户是主体）和产品发现用户的社会关系（用户是对象）。这个产品的红线一直是后者，放宽前者不动这条红线。而且不接渠道的代价很实际——要求全家搬到一个新 App 里，这在真实世界不成立 |

## 12. 风险与待确认事项

| 风险 / 待确认 | 影响 | 应对 | 负责人 |
| --- | --- | --- | --- |
| 产品被看成「又一个 AI 助手」 | 直接失去记忆点 | 首页坚决不做成聊天框；路演开场讲「目录所有权」的迁移故事；Demo 第 4、5 步是差异化证明 | 待定 |
| 五阶段归属字段实现太晚 | 核心报告只能靠模型编，追问即崩 | 列为 P0 第一项，先落库再做别的 | 待定 |
| 大模型输出不稳定，现场翻车 | Demo 中断 | Schema 校验 + 重试一次 + 失败降级为待人工确认；关键演示步骤预置兜底结果 | 待定 |
| 看护升级链无法在 4 分钟内演完 | 最有分量的功能演不出来 | 演示速度开关，超时压到 60 秒 | 待定 |
| 同意门增加交互步数，被认为啰嗦 | 体验评价下降 | 只在首次和敏感类目询问；同类事项支持「以后这类都告诉家里人」；把这一步作为讲点而不是负担。V1.2 之后这条压力小了一些：没进家的人根本不会遇到同意门 | 待定 |
| 健康信息合规风险 | 上线风险 | 健康类结论默认 `care_related` 可见；明确非医疗设备；不做诊断与用药建议 | 待定 |
| 高风险内容（自伤 / 家暴 / 急性症状）处置不当 | 严重后果 | 边界 Agent 不生成任务，给出专业资源提示，不做诊断；此路径必须在 Demo 前测试 | 待定 |
| 老人真实可用性未验证 | 核心假设不成立 | 赛前找 2–3 位真实长辈试用被看护人侧界面，只验证「能不能自己回应一次提醒」 | 待定 |
| 大模型 API 成本与延迟 | 现场卡顿 | 主用国内模型；见证 Agent 只发最小上下文；非实时分析走批处理 | 待定 |
| 「不指责」的表达尺度难把握 | 产品调性崩塌，变成夫妻矛盾放大器 | 报告文案全部人工撰写模板，不由模型自由生成；只做分布陈述不做归因 | 待定 |
| 3 天内做完 13 项 P0 | 交付风险 | 严格按 7.2 顺序做；第 2 天结束若 P0 未过半，砍语音、砍截图、砍连接中心、砍家庭群（只留 1:1）。**不砍「没进家不产生数据」这个闸门，也不砍交不过去的状态**，这两项是差异化本身 | 待定 |
| **「没进家就不产生数据」被做成了 UI 层的隐藏** | 如果只是界面上不显示，但数据已经写进去了，这条隐私承诺就是假的。一旦被追问代码，比不做这个功能更糟 | 列为 P0 第 2 项，做成**数据层的闸门**：`User.joinedFamilyAt` 为空时见证产出一律丢弃，不写 `Evidence`、不写 `Signal`、不弹同意门。写成可执行断言：说一句家里的事，断言记录条数不变 | 待定 |

## 13. V2 展望

1. **多家庭空间**：一个人同时属于原生家庭和自己的小家庭。这是目标用户的真实处境，只支持一个家等于只解决一半问题。V1.1 曾把它提到 V1，V1.2 又收回（决策 #15），但做法已经想清楚了：

   - 会话归属哪个家，用户点进哪个会话说话时就已经决定了。**不问用户，也不让模型猜。**
   - 跨空间零泄漏是头号硬边界：所有查询强制带 `spaceId`（缺失即拒绝，禁止隐式默认当前空间）、模型上下文按空间裁剪、成员看不到别的空间存在。
   - 报告按空间独立统计，**不做跨空间总分**。「你在两个家一共多累」这种数字不该存在。
   - 必须配一组可执行的隔离验证用例，而不是靠人工点查。

2. **空间内的成员分组**：夫妻俩先商量好再告诉老人；兄弟姐妹之间协调轮流照顾。`visibility` 增加 `group:[...]` 取值。注意分组是**可见性工具，不是权限层级**，而且责任域的主人始终是一个人——「交给一个组」等于没有主人。
3. **外部照护者角色**：保姆 / 护工纳入空间，带权限隔离与交接留痕，是明确的付费点。
4. **责任域模板库**：老人复查、孩子入学、宠物疫苗、房屋报修等预置模板，降低冷启动成本。
5. **长期趋势**：责任集中度的月度 / 季度变化，观察交接是否真的持续有效（而不是交完又回流）。
4. **设备联动作为回应来源**：智能药盒、可穿戴设备**自动产生 `ack`**，减少对被看护人主动操作的依赖。注意这与 4.10 的播报是相反方向——播报是输出，这里是输入，而且它能真正提高送达证据的质量。
5. **播报设备的双向化**：让机器人 / 音箱接收一句「吃了」并回传为 `ack`。一旦做成，播报就从「只能输出」升级为可以满足 `requireAck` 的通道，4.10.2 的限制可以放开。这是播报能力最有价值的下一步。
6. **空间上限放开与跨空间视图**：在验证过隔离足够可靠之后，谨慎提供一个用户自己可见的跨空间总览。**仍然不做跨空间总分**。
7. **真实消息渠道**：在合规前提下接入更多输入通道。

> 关于多空间的来回：V1.1 曾把它从 V2 提到 V1，V1.2 又收回 V2（决策 #15）。这不是反复无常——提上来是因为它确实是目标用户的真实处境，收回去是因为它带来的头号风险（两个家的信息串台）在 96 小时里不值得同时赌。做法已经想清楚了，V2 接着做的成本不高。
>
> 关于设备联动：原 V2 第 5 项拆成了现在的第 6、7 两项，因为方向不同。作为**回应来源**才是它真正的价值，作为**播报输出**只是提高触达。
