## 0. 怎么读这份文档

**这份文档不替代 PRD，它只做两件事：**

1. 说清楚 Ohai 有什么、我们有什么、差在哪（第 2 章对比矩阵）。
2. 把差距转成**编号的、可领的、带验收标准的任务**（第 3–5 章）。

**三条硬性约定，请先读：**

| # | 约定 |
| --- | --- |
| 1 | **本文档的所有优化项都是追加项，不得挤占 PRD 7.2 的 13 项 P0。**排期见第 6 章。任何一项优化项与 P0 抢人，优先做 P0 |

**术语沿用 PRD。**特别注意 PRD 6.5 的禁用词表在本文档同样生效：写代码时字段名可以用 `primary/partner/subject`，但任何进 UI 的字符串不许出现责任身份词。

## 1. 结论先行

**Ohai 是目前和《都记得》最贴身的对位产品，不只是同赛道，连叙事都撞了。**它的官网通篇讲 mental load / invisible load，创始人是 Care.com 的 Sheila Lirio Marcelo，产品已上 App Store 与 Google Play，按人数分三档订阅（约 9.99 / 19.99 / 29.99 美元每月）。

但它的功能面几乎全部落在**捕获与分配**，没有一寸落在**归属与交接**：

- 它没有任何字段记录「谁发现了这件事」「谁在盯截止时间」「谁在跟进结果」。
- 它的官方 FAQ 明说 **O 不会自己分配任务**，只能由用户指派，或者请 O 去问某人一句。
- 所以它的产品逻辑最终仍然是「你来分配，我来传达」——**主责任人还是那个分配者。**

这就划出了借鉴边界：

> **捕获层和呈现层大方抄，归属主轴不动。**

**同时要正视一个变化：**「隐形劳动」这个开场故事已经不是我们独占的了。PRD 2.3 那个「多 Agent 目录所有权迁移」的立论来源因此更重要——它是我们唯一真正独有的东西。相关答辩口径见第 8 章。

## 3. 优化项清单 · P0 追加（建议本次一定做）

三项共计约 **11 小时**。选它们的标准是：**成本低、直接强化核心立论、且有现场演示价值。**

---

### OPT-01 无主责任域不发提醒

| | |
| --- | --- |
| 优先级 | **P0 追加 · 排第一** |
| 工时 | 1.5h |
| 依赖 | 无 |
| 借鉴来源 | Ohai 的硬规则：没有 owner 的 to-do 不发提醒，因为没人可催 |

**为什么做**

我们现在把「无主责任域」当成一个**展示状态**（`ownerless` 只在报告里出现一个数字）。Ohai 把它做成了**有行为后果的状态**。

这条改动的价值不在功能，在立论：产品说「责任不能落到地上」，那就不能一边说没人管、一边照旧给全家发提醒。**照旧发提醒等于默认了那个「顺手接住」的人还在接。**

**要做什么**

1. 责任域 `ownerId` 为空时，其下所有任务**不产生任何提醒**。
2. 取而代之，在首页的「没人管的责任」一节里显示：`这一块还没有主人，所以没有人会收到提醒`。
3. 该节提供唯一动作：**发起交接**（复用 `proposeHandover()`）。

**验收标准（可执行断言）**

- [ ] `d_health`（Fixture 里唯一无主的责任域）在任何角色的界面上都不产生提醒条目。
- [ ] 断言：`ownerId === null` 的责任域下的任务数 > 0，但生成的提醒数 === 0。
- [ ] 交接完成（`acceptHandover()` 执行后 `ownerId` 变为 `dad`）时，同一批任务的提醒数由 0 变为 > 0。这条要能当场演示。
- [ ] 无主节的文案不出现任何责任身份词（过 PRD 6.5 检查）。

**改动点**

- `data.js`：新增 `remindersFor(userId)` 派生函数，第一行就过滤掉 `!domainOf(t.domainId).ownerId`。
- `app.js` `mapView()` / `dutyView()`：无主节增加那句说明与「发起交接」按钮。

**红线检查**

- PRD 4.7「提醒只发给责任域的主人，系统不承担帮 A 提醒 B 的角色」——本项是这条的严格化，不冲突。
- 不得因为「没提醒了会不会漏」而加一个兜底提醒给主责任人。**那正是要消灭的东西。**

### OPT-02 待办三视图切换

| | |
| --- | --- |
| 优先级 | **P0 追加** |
| 工时 | 4h |
| 依赖 | 无（`agenda()` 已有） |
| 借鉴来源 | Ohai 的 Member View：一条大列表 / 按人分组（每人一栏 + O 一栏 + 未分配一栏） |

**为什么做**

PRD 4.7 已经调和过口径：「时间表是视图，责任归属是主轴」。但原型只实现了按日期一种视图。Ohai 证明了**按人看**是用户会主动切的，而且它那个「未分配单独一栏」正是我们要的东西。

我们比它多一种：**按责任域**。三个视图同时存在，才真正说明「视图可换、主轴不丢」不是一句话。

**要做什么**

在「家里」页的待办区顶部加一个三选切换：

| 视图 | 分组键 | 排序 |
| --- | --- | --- |
| 按日子 | `t.dueAt`（已实现） | 日期升序，`没定日子` 落底 |
| 按人 | 责任域主人（**不是 `executedBy`**） | 成员按 `ORDER`，末尾追加「还没有主人」一栏 |
| 按责任 | `t.domainId` | 无主责任域**排在最前** |

**每条待办卡在三种视图下都必须显示：所属责任域名称 + 这一块的主人（没有就标出来）。**这是主轴，不随视图变。

**验收标准**

- [ ] 三个视图之间切换，可见的待办总数完全一致（只是分组不同，不许某个视图偷偷过滤）。
- [ ] 按人视图末尾有「还没有主人」一栏，且它不是空的（Fixture 里 `d_health` 无主）。
- [ ] 按人视图的分组键是**责任域主人**，不是执行人。用 `t8`（`executedBy: "dad"`，但责任域主人是 `mom`）验证：`t8` 必须出现在妈妈那一栏。
- [ ] 任意视图下随机抽一条卡，都能读出它的责任域和主人。
- [ ] 切换视图不触发任何模型调用（纯前端分组）。

**改动点**

- `data.js`：`agenda(userId)` 改为 `agenda(userId, groupBy)`，`groupBy ∈ {"day","owner","domain"}`，返回结构保持 `[{key, label, items}]` 不变。
- `app.js` `agendaBlock()`：加切换控件，读写 `S.ui[actor].agendaView`。
- `data.js` `seed()`：`ui` 每个角色加 `agendaView: "day"`。

**红线检查**

- **按人视图不许出现红色堆积。**某一栏全红等于事实上的懒惰排行榜，直接违反 PRD 4.4.3 禁止清单和 6.3「不给任何成员标红」。逾期只在**按日子**视图标红，且标的是事不是人。这条与 OPT-08 有耦合，两项要一起验收。
- 分组标签用家庭称谓（`roleName()`），不许出现责任身份词。

### OPT-03 语音一次多条拆分

| | |
| --- | --- |
| 优先级 | **P0 追加** |
| 工时 | 5h（含 Fixture 与动效） |
| 依赖 | 见证 Agent（P0 第 5 项）必须先跑通 |
| 借鉴来源 | Ohai 的 voice brain dump：一句话塞三件事，AI 拆成三条 |

**为什么做**

这是**唯一一个几秒钟就能让人懂「AI 在替你记」的动作**，性价比高于截图识别（PRD 7.3 把语音和截图都放在 P1，建议把语音提上来、截图留在 P1）。

Ohai 给的场景描述值得照抄进演示脚本：正在开车、正在做饭、刚想起三件事。这恰好是主责任人的真实处境。

**要做什么**

1. 长按麦克风 → 一段预置真实语音（PRD 4.2 允许 MVP 只做一条预置演示）。
2. 转写文本一次性上屏，内容含**三件事 + 一句纯闲聊**。建议台词：

   > 「哦对，奶奶那个报告我还没找到，体检表周五之前得交，还有下周三下午要请个假陪她去医院。今天太累了。」

3. 见证 Agent 拆成 **3 条信号 + 1 条不建任务**，逐条以 stagger 动效落进列表。
4. 第 4 句「今天太累了」必须**明确显示被识别为不建任务**，理由可点开看。

**验收标准**

- [ ] 一次输入产出 3 条候选任务，不是 1 条长文本任务。
- [ ] 第 4 句进 `status: "observing"` 池，`why` 字段有人类可读理由，界面上可点开。
- [ ] 3 条候选各自带责任域归属推断（两条进 `d_health`，一条进 `d_school`）。
- [ ] 这一步在「没进家」状态下执行时，**记录条数断言不变**（复用 PRD 12 章那条断言，不许因为走了语音路径就绕过 `joined` 闸门）。
- [ ] 拆分结果可逐条否掉，否掉写 `AuditLog`。

**改动点**

- `data.js`：`send()` 增加多条拆分分支；`FAMILY_HINTS` 按句切分后逐句过。
- `app.js` `composer()`：长按态与转写上屏动画；新增 `card: "voiceSplit"` 卡片类型。
- 新增 Fixture：一段音频文件 + 预置转写文本（不要用 TTS 现场合成，延迟不可控）。

**红线检查**

- **`joined` 闸门优先于一切输入形态。**语音是输入通道，不是绕过闸门的理由。这条必须写成测试而不是靠自觉。
- 拆分结果是**候选**，不是已确认任务。进家庭库仍然要过同意门（PRD 4.3.2）。

### OPT-04 未确定事项改成可点建议卡

| | |
| --- | --- |
| 优先级 | P1 · 排第一 |
| 工时 | 3h |
| 依赖 | 交接包（P0 第 9 项） |
| 借鉴来源 | Ohai 的智能后续建议：追加几个可点的关联步骤，点了才进列表，不点就消失 |

**为什么做**

交接现在卡在 blocked 时，补齐动作是 `fillInfo()` 一键填。这在演示里够用，但形态是错的——它暗示「补信息」是填表。

Ohai 那个「可点、不点就消失」的交互，**正好是我们「未确定事项」的正确形态**：不弹表单、不增加打扰、点一下就补上一格。

**要做什么**

1. 交接卡的 `missingInfo` 每一项渲染成一张可点的小卡，附一个**AI 建议的答案**（来自证据链）。
2. 例：缺「挂哪个科」→ 卡上写 `骨科（来自 7/15 那句话）`，点一下即填入并溯源。
3. **不点就留在原处**，不消失、不催促。这一点和 Ohai 不同：他们的建议不点就没了，我们的必须留着，因为它是 blocked 的原因（PRD 6.3 要求视觉突出）。

**验收标准**

- [ ] 每个 `missingInfo` 项旁有可点建议，且建议带证据 ID，可溯源到原话。
- [ ] 点击后该项 `filled = true`，`refreshHandover()` 重算状态，blocked 在两项都补齐后才解除。
- [ ] 建议**不自动填**。没点就是没填，状态照旧 blocked。
- [ ] 无建议可给时显示为空白待补项，不许编一个建议出来。

**改动点**

- `data.js` `proposeHandover()`：`missingInfo` 每项加 `suggestion` 与 `suggestionEvidenceId`。
- `app.js` `sheetContent()` 交接抽屉分支：渲染建议卡。

**红线检查**

- PRD 决策 #7「绝不默认成功」——建议**只是建议**，点击是人的动作。自动填等于默认成功。
- 建议来源必须是真实证据，不能是模型编的。无据可依就留空。

### OPT-05 责任域可以由 Agent 承担

| | |
| --- | --- |
| 优先级 | P1 |
| 工时 | 4h |
| 依赖 | OPT-01 |
| 借鉴来源 | Ohai 可以把 to-do 指派给 O，O 真去做（每周三查周末活动），且**指派给 O 的任务不发提醒** |

**为什么做**

这是本次调研里**概念增量最大的一项**。

我们现在对 `ownerId` 只有两种解：为空（没人管）或某个成员（有人管）。但**有些无主责任域交给谁都是负担，交给 Agent 才是真的减负。**Ohai 已经验证了用户愿意这么用。

它给了我们第三种解：`ownerId = "agent"`。

**要做什么**

1. `Domain.ownerId` 允许取值 `"agent"`。
2. 交接提议的接手人选项里增加一个：**交给「记得」自己**。对无主责任域和已有主人的责任域都可选（后者是主责任人主动卸给 Agent，这恰恰是她最想要的那种减负）。
3. Agent 持有的责任域：不发提醒（无人可催），改为**到期主动汇报结果**。
4. 集中度报告里 Agent 单独一栏，**不计入任何成员的隐形劳动占比**。

**判定什么能交给 Agent（白名单，不由模型自由决定）**

| 能交 | 不能交 |
| --- | --- |
| 查信息、比较、整理、按时汇报 | 任何需要到场的事 |
| 记时间、盯截止、生成清单 | 任何有身体后果的事 |
| —— | **所有 `CareRule` 相关的一切** |

**验收标准**

- [ ] Fixture 里 `d_home`（家里的日常补给与收纳，现主人是妈妈）可以由妈妈交给 Agent，交接后 `ownerId === "agent"`，妈妈的「只有你在记得」相应减少。
- [ ] Agent 持有的责任域不产生提醒（复用 OPT-01 的过滤器）。
- [ ] 报告里 Agent 单独成栏，`invisibleBy` / `allBy` 里成员的数字不受影响。
- [ ] 尝试把任何关联 `CareRule` 的责任域交给 Agent，**必须被拒绝并给出理由**。这条要写成断言。
- [ ] 界面上称它「记得」（产品名），不叫「AI」「机器人」「系统」。

**红线检查**

- PRD 4.6.1 与决策 #5：看护有真实后果，**必须由人确认、由人承担**。看护责任域交给 Agent 是对这条的直接违反，必须 fail-closed。
- 交给 Agent 仍然要走双方确认吗？**要**，提出方确认一次。Agent 侧的「确认接收」由白名单判定代替，判定不过就是 declined。不许因为对方是 Agent 就跳过状态机。

### OPT-06 每日一屏

| | |
| --- | --- |
| 优先级 | P1 |
| 工时 | 4h |
| 依赖 | OPT-02 |
| 借鉴来源 | Ohai 的 Daily Dump：早晚各一次，日程 + 待办 + 提醒 + 冲突 + 天气，逐段带你过一遍 |

**为什么做**

Ohai 的 Daily Dump 反过来验证了 PRD 4.7 那次口径调和是对的：**纯按责任域分组不好用，用户真的需要「今天要干什么」。**

但我们的顺序必须和它相反。它是「日程优先，待办附在后面」；我们是**「这周只有你在记得」必须排在时间表之前**（PRD 4.7 硬性要求）。这个顺序差异就是两个产品的差异。

**要做什么**

一屏，从上到下固定三段：

1. **这周有 N 件事一直只有你在记得** —— 复用 `onlyIRemember()`，可展开。
2. **今天** —— 复用 `agenda()` 的当日切片，每条带责任域与主人。
3. **没人管的** —— 复用 OPT-01 的无主节。

**明确不做 streak。**见第 5 章。

**验收标准**

- [ ] 三段顺序固定，第 1 段永远在第 2 段之前，不许因为「今天没事」就把它挪下去。
- [ ] 第 1 段的数字与左侧 rail 的实时指标一致（同一个 `onlyIRemember()`）。
- [ ] 交接完成后，第 1 段数字当场下降。这是 Demo 第 11 步的情绪落点，必须在这一屏上可见。
- [ ] 无打卡、无连续天数、无任何计分。

**改动点**

- `app.js` `mapView()`：重排为三段结构，`agendaBlock()` 传入当日切片。

**红线检查**

- PRD 6.3「数字用于呈现分布，不用于打分。不出现总分、等级、排名」。
- 「只有你在记得」这段的文案不许出现「你最累」「你承担最多」这类定性（PRD 6.5）。只陈述事实：`这周有 7 件事，四个环节都只有你一个人`。

### OPT-07 交接询问通道

| | |
| --- | --- |
| 优先级 | P1 |
| 工时 | 3h |
| 依赖 | 交接状态机（P0 第 9 项） |
| 借鉴来源 | Ohai 的委派协商：「O，问一下 Alex 今天能不能接孩子」→ O 直接去私聊他确认 |

**为什么做**

**原样抄会直接撞我们两条红线**（PRD 4.7「系统不承担帮 A 提醒 B 的角色」、4.2 群聊行为红线）。但改造后它恰好是我们缺的一块管道。

区别在粒度：

| | Ohai | 我们 |
| --- | --- | --- |
| 传递什么 | 替你去催一次执行 | 替你去问一次接不接整块责任 |
| 发生几次 | 每次都要问 | 交接时问一次，之后不再问 |
| 结果 | 对方答应了这一次 | 所有权真的转移了 |

改造后不违反红线，因为它传递的是**所有权询问**，不是催办。

**要做什么**

1. 交接进入 `pending_ack` 时，Agent 在接手人的 1:1 对话里发一张交接卡。
2. 卡上三个动作：**接下来 / 先看看细节 / 现在接不了**。
3. 「现在接不了」→ `declined`，且**不追问、不再发第二次**。
4. 提出方只看到状态变化，**看不到任何理由文本**。对方没义务解释。

**验收标准**

- [ ] 交接卡出现在接手人的 `agent_dm`，不在家庭群。
- [ ] 同一次交接**最多发一次**。断言：`pending_ack` 状态下重复触发不产生第二条消息。
- [ ] `declined` 后提出方界面只显示「对方暂时接不了」（`hStatus()` 已有此文案），无理由、无追问入口。
- [ ] Agent 发出的这条消息不含任何评价性词汇（复用 PRD 6.5 的自动检查扫这条模板）。

**红线检查**

- PRD 4.2:「不评价成员、不催促特定人、不代替某人向另一人表达不满」。这条卡的文案必须是**模板**，不是模型自由生成。
- 不做「已读未回则再问一次」。**再问一次就是催办**，就变回了协调劳动。

### OPT-08 逾期标事不标人 + 分类图标

| | |
| --- | --- |
| 优先级 | P1 |
| 工时 | 2h |
| 依赖 | OPT-02（**必须同批验收**） |

- [ ] 逾期信息在不看颜色的情况下仍可读（灰度截图验证）。
- [ ] 分类图标只标事，不标人。

**红线检查**

- PRD 4.4.3 禁止清单、6.3「责任集中度表用中性色，不给任何成员标红」。
- PRD 6.2 无障碍：颜色不承载唯一信息。

## 8. 从 Ohai 身上学到的三件非功能的事

这三条比功能清单值钱，请团队都读一遍。

### 8.1 最该重视的一条教训：「喜欢这个想法，但不知道怎么用」

这是 Ohai 自己写在产品重构公告里的话（大意），也是他们推倒重来的直接原因。他们的结论是：**一旦产品增加了心智负担而不是卸掉负担，就彻底跑偏了。**

**对我们是直接威胁。**数一下用户要理解的概念：密钥门、同意门、三张版式、「这不是我的情况」、交接的 blocked 状态。**五个。**

PRD 12 章已经列了「同意门增加交互步数，被认为啰嗦」这条风险，但 Ohai 的教训说明这个风险被低估了——问题不是啰嗦，是**用户不知道下一步该干什么**。

**建议加一条验收标准：**

> 进家后的首屏必须有一个明确的、单一的下一步动作按钮，不能只是一张责任地图让人自己看。

OPT-06 的三段结构就是这条的落地：第 3 段「没人管的」永远给出一个动作（发起交接）。

### 8.2 「响了一声不等于事情做了」

Ohai 最近把 reminder 强制绑进 to-do，理由是用户反馈：**一声提醒不能证明任何事发生了，尤其当该动手的是伴侣或小孩。**

这和我们的 PRD 4.10.2（播报 `accepted_unverified` 单独一档）、4.11.2 第 6 条（返回 202 不代表送到人）是**完全同一条原则**，而且我们已经推得比他们远。

**这一点在答辩时可以主动讲：**一个已经融资、已经上架的竞品，是在上线一年多之后才补上这条认知的；我们从第一版设计就把「送达、听见、做完」分成三件事。这不是运气，是决策 #7 的必然结果。

### 8.3 他们的产品纪律：95% 可自动化才允许上线

创始人给团队定的标准是：一个功能要上线，AI 得能完成其中 95%。

我们的对位物是 5.3「校验失败降级为待人工确认」和决策 #7 的 blocked-by-default。**我们的标准其实更严：**

| | Ohai | 我们 |
| --- | --- | --- |
| 标准 | 够好才上 | 不够好就停住，**并且说出来** |
| 剩下那部分 | 不上线 | 显式暴露成 blocked 状态 |

这个对比在答辩时很有力，建议写进第 9 章。

### 8.4 建议加进 PRD 第 9 章的答辩条目

| 可能的追问 | 回答 |
| --- | --- |
| **这和 Ohai.ai 有什么不同？** | Ohai 解决的是信息散落——把邮件、PDF、学校通知收拢成一份共享日历和待办，这一块它做得比我们好。但它没有回答更根本的那个问题：**收拢完了，谁负责记得。**它能把一条任务指派给伴侣，却没有任何字段记录是谁发现了这件事、谁在盯截止时间、谁在跟进结果。所以它的产品逻辑最终仍然是「你来分配，我来传达」，主责任人还是那个分配者。我们做的是另一半：五阶段归属是数据库一等字段，所以我们能指出协调工作集中在谁身上，能提议把一整块责任交接出去，并且在信息不全时**让交接停在 blocked**，而不是假装成功。它切的是第 4 步执行，我们切的是另外四步 |
| **「隐形劳动」这个概念别人也在讲，你们的独特性在哪？** | 概念不独特，**度量方式独特**。讲隐形劳动的产品很多，但没有一个把「发现、记时间、安排、执行、跟进」拆成五个数据库字段。没有这五个字段，「谁在承担」只能靠用户自己说，而真正的主责任人往往不觉得自己在承担额外劳动——这恰恰就是隐形劳动的定义。所以我们的立论必须建立在度量上，不能建立在共情上 |

> **提醒：开场如果只讲「妈妈很累」，评委听过了。**PRD 2.3 那个多 Agent 目录所有权的迁移故事是我们唯一真正独有的立论来源，它现在比之前更重要。
